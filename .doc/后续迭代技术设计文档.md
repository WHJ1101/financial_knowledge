# Financial Knowledge 后续迭代技术设计文档

> 日期：2026-07-02
> 配套文档：`.doc/后续迭代需求文档.md`
> 设计来源：`.doc/项目评审报告.md`
> 设计目标：以小步迭代修复核心体验，同时把浅 Module 加深，提升 Locality 与 Leverage

---

## 1. Design Goals

1. 补齐报告删除、搜索落地、任务页收敛这三个 P0 体验缺口。
2. 用真实 SQLite Adapter 替换 sql.js 全量落盘，保留上层调用习惯。
3. 将报告生产、任务执行、前端数据加载从“大而全”入口里拆出来。
4. 保持单实例、本地优先的部署模型，不引入多用户和分布式复杂度。
5. 用测试保护迁移过程，避免投研数据损坏。

## 2. Current Architecture Summary

当前项目由四层构成：

- 前端：Preact + signals，hash route，`src/pages` 承载页面，`src/store.js` 做全局数据加载。
- 后端：Node 原生 HTTP，`server/index.js` 做 API 分发、静态文件、报告生成、日更编排。
- 数据：sql.js 内存数据库，全量导出到 `data/app.db`。
- Pipeline：`lib/` 下研究、每日简报、社群信号、LLM client 等纯逻辑与外部数据采集。

主要技术摩擦：

- `server/index.js` 承担太多领域职责，HTTP Module 偏浅。
- `server/services/db.js` 的 Interface 看似兼容 better-sqlite3，但 Implementation 有写放大、假事务和单进程限制。
- `src/store.js` 的 `refresh()` Interface 过宽，页面依赖不清晰。
- `Portfolio.jsx` 视图实现集中，计算 Module 已变深但视图 Locality 不够。
- 报告元数据和 HTML 文件双写，删除和一致性尚未形成统一 Module。

## 3. Target Module Map

### 3.1 Storage Module

**Purpose**：提供稳定、真实事务的 SQLite 存取 Interface。

**Interface**：

- `prepare(sql).run(...params)`，返回对象必须保留 `.changes`。
- `prepare(sql).get(...params)`
- `prepare(sql).all(...params)`
- `exec(sql)`
- `transaction(fn)`
- `DATA_DIR`
- `DB_PATH`

**Implementation**：

- 使用 better-sqlite3 打开 `data/app.db`。
- 启用 `PRAGMA journal_mode = WAL` 和 `PRAGMA foreign_keys = ON`。
- 保留 DDL 初始化和 Safe ALTER 逻辑。
- `transaction(fn)` 使用 better-sqlite3 原生事务。
- Adapter 必须保留现有 sql.js wrapper 的载荷行为：`undefined -> null`，布尔值 `true/false -> 1/0`，避免 better-sqlite3 绑定参数时报错。
- `run()` 返回契约继续暴露 `.changes`，兼容现有删除和替换逻辑。
- better-sqlite3 模块改为同步初始化；迁移后需要真实起服务确认不存在依赖顶层 await settle 的隐式时序。

**Adapter Plan**：

- 当前 sql.js wrapper 替换为 better-sqlite3 Adapter。
- 上层 routes/services 不直接感知 Adapter 变化，但 Adapter 内部要显式写出参数归一化契约。
- Dockerfile 必须随 native dependency 同步更新：要么在 Alpine deps 阶段安装 `python3 make g++`，要么切换到同一 Node 版本的 Debian slim 镜像；deps/runtime 必须保持同一 Node ABI 和 libc。
- 如需测试隔离，可提供临时 DB 路径环境变量。

### 3.2 Report Lifecycle Module

**Purpose**：统一报告写入、读取、删除、文件一致性。

**Proposed Modules**：

- `ReportWriter`：负责创建/导入报告时写 HTML、写 DB、写日志。
- `ReportRepository`：负责 reports 表查询、标星、归档、标已读、删除。
- `ReportFileStore`：负责报告 HTML 路径生成、写入、删除、存在性检查。

**Key Interface**：

- `createResearchReport({ topic, type, source })`
- `importExternalReport(body)`
- `deleteReport(id)`
- `getReport(id)`
- `listReports(filters)`
- `markReportRead(id)`
- `toggleReportStar(id)`
- `archiveReport(id)`

**Deletion Contract**：

- `DELETE /api/reports/:id`
- 成功返回 `{ deleted: true, fileDeleted: boolean }`
- id 不存在返回 404。
- 文件不存在但 DB 存在时，删除 DB 并返回 `fileDeleted: false`。
- 删除动作写入 logs。

### 3.3 Search and Knowledge Module

**Purpose**：让全局搜索有明确落地位置。

**Approach**：

- 顶栏搜索输入后更新全局 `query`，并跳转 `#knowledge?q=...`。
- Knowledge 页面负责展示搜索词、筛选组合和空态。
- 搜索词必须编码进 hash query，例如 `#knowledge?q=光模块`，刷新后由 hash 恢复。
- 新增 `parseHashQuery(hash)` / `buildKnowledgeHash(filters)` 纯函数，单测覆盖中文、空值、清空搜索。

**Preferred Decision**：

- v0.3 直接采用 `#knowledge?q=...`，满足“刷新可恢复”的需求验收。
- 后续可扩展为 `#knowledge?q=...&origin=...&topic=...`，把筛选条件也放入 hash query。
- 搜索跳转前避免空搜索和误触导致当前页未保存表单丢失；必要时仅在非空搜索词时跳转。

### 3.4 Task Execution Module

**Purpose**：让任务 UI 与真实执行能力一致。

**Short-Term Design**：

- 任务页只展示内置每日简报任务。
- 隐藏自由创建表单。
- 保留已存在的自定义任务数据，但归入“不可执行/规划中”区域，默认折叠或不展示。
- 合并当前三处“是否每日任务”判定：后端提供单一 `isDailyBriefingTask`，`formatTask` 输出 `executable`，前端只消费 `task.executable`，不再以名称正则重复判断。

**Future Seam**：

当确实需要多个自动化时，引入：

- `task.type`
- `task.enabled`
- `task.schedule`
- `TaskExecutorRegistry`
- `registerTaskExecutor(type, executor)`

至少有两个真实 executor 后，再把任务类型作为稳定 Seam。

### 3.5 Page Data Loading Module

**Purpose**：替代全量 `refresh()`，让页面数据依赖更清晰。

**Current**：

- `App` 在多数路由变化时调用 `refresh()`。
- `refresh()` 同时加载 status、reports、stocks、positions、decisions、signals、tasks、logs、market。

**Target Interface**：

- `loadShellData()`：status + market snapshot。
- `loadTodayData()`：status + reports + market。
- `loadKnowledgeData()`：reports。
- `loadPortfolioData()`：stocks + positions + market indices。
- `loadSignalsData()`：signals。
- `loadDecisionsData()`：decisions + status。
- `loadTasksData()`：tasks + logs + status。
- `loadSettingsData()`：status。

**Migration Strategy**：

- 保留 `refresh()` 作为兼容 wrapper，但设置退出条件：v0.4 完成后仅允许登录成功后的首屏加载临时调用；路由级 `refresh()` 必须清零。
- 页面逐步改用自己的 loader。
- v0.5 起删除 `refresh()` 本体或将其降级为测试辅助。
- 顶栏 market 轮询继续独立。

### 3.6 Status Date Contract

**Purpose**：消除前端解析中文展示字符串的脆弱耦合。

**API Change**：

`GET /api/status` 增加：

```json
{
  "today": "2026-07-02",
  "nowIso": "2026-07-02T02:30:00.000Z",
  "nowDisplay": "周四 · 2026-07-02 10:30:00"
}
```

保留旧 `now` 字段一段时间，避免一次性改动过大。

**Frontend Change**：

- Today 使用 `status.value.today`。
- Signals 使用 `status.value.today`，fallback 到本地 `localToday()`。
- 显示时间使用 `nowDisplay || now`。

**Split Plan**：

## 4. Data Model Changes

### 4.1 Report Deletion

No schema change required for hard delete.

Recommended behavior:

- Hard delete by default for personal cleanup.
- Existing `archived` remains soft-hide.
- Add log entry with report id/title.

Optional future extension:

- `deleted_at` soft delete if undo is needed. Not required for v0.3.

### 4.2 Task Type

Short term no schema change required.

Future extension:

```sql
ALTER TABLE automation_tasks ADD COLUMN type TEXT DEFAULT 'custom';
```

Suggested type values:

- `daily-briefing`
- `custom`

Do not add this until UI and executor registry are ready.

### 4.3 Manual Quote Override

Suggested table:

```sql
CREATE TABLE IF NOT EXISTS quote_overrides (
  code TEXT PRIMARY KEY,
  name TEXT,
  market TEXT,
  price REAL NOT NULL,
  change_pct TEXT,
  source_label TEXT DEFAULT '手动行情',
  note TEXT,
  updated_at TEXT NOT NULL
);
```

Usage:

- Quote lookup first tries live quote.
- If live quote fails, fallback to override.
- 回退逻辑放在后端 `getStockQuote` 这个单一行情出口，前端和未来批量报价接口不重复实现 fallback。
- UI must show source label.

### 4.4 Report Asset Links

Suggested table:

```sql
CREATE TABLE IF NOT EXISTS report_asset_links (
  id TEXT PRIMARY KEY,
  report_id TEXT NOT NULL,
  asset_code TEXT NOT NULL,
  asset_name TEXT,
  asset_market TEXT,
  relation TEXT DEFAULT 'related',
  source TEXT DEFAULT 'manual',
  created_at TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_report_asset_links_report ON report_asset_links(report_id);
CREATE INDEX IF NOT EXISTS idx_report_asset_links_asset ON report_asset_links(asset_code);
```

Suggested relation values:

- `mentioned`
- `thesis`
- `risk`
- `decision`
- `related`

## 7. Backend Design

### 7.1 Route Table Refactor

Short-term can keep current `handleApi` if/regex structure for v0.3.

When entering v0.4 or v0.6，建议引入极简 route table：

```js
[
  { method: "GET", pattern: /^\/api\/status$/, handler: handleStatus },
  { method: "DELETE", pattern: /^\/api\/reports\/([^/]+)$/, handler: handleDeleteReport }
]
```

Benefits:

- HTTP Module 更薄。
- 新增 API 不继续拉长 `handleApi`。
- handler 更容易单测。
- Auth 仍应在路由分发前或 route table wrapper 中统一处理，避免每个 handler 自己散落鉴权判断。

### 7.2 Report Delete Flow

Flow:

1. Auth check.
2. Load report by id.
3. Resolve report file path through ReportFileStore.
4. 校验 resolved path 必须位于 `REPORT_DIR` 内，复用 `serveFile` 同类 path traversal 防护。
5. v0.3 在 sql.js 下先删除文件，再删除 DB row，再写日志。`ENOENT` 视为文件已不存在并继续；其他文件删除错误应阻止 DB 删除并返回错误。
6. Return deletion result.

Transaction:

- v0.3 无真事务时采用“先删次要副本文件、后删主索引 DB”的顺序，避免 DB 已删但 HTML 成为不可追踪孤儿文件。
- v0.4 迁移 better-sqlite3 后，DB delete + log should be in transaction；文件删除放在事务提交前后需按实现细节评估，但必须保留 path 安全和 orphan cleanup 测试。

### 7.3 Storage Migration

Steps:

1. Add better-sqlite3 dependency.
2. Replace `server/services/db.js` Implementation while preserving exports.
3. Preserve Adapter parameter normalization: `undefined -> null`, booleans -> `0/1`; preserve `.run().changes`.
4. Keep DDL and ALTER logic.
5. On startup, open existing `data/app.db`.
6. Update Dockerfile for better-sqlite3 native dependency; with Alpine install `python3 make g++` in deps stage, or switch deps/runtime to matching Debian slim images.
7. Run integrity smoke checks.
8. Run test suite.
9. Run real service startup against a copy of existing `data/app.db`.
10. Run `docker compose up -d --build` and verify container startup.

Backup:

- Do not write backup into Git.
- On startup migration, optional copy `data/app.db` to `data/backups/app-YYYYMMDD-HHmmss.db`.
- Backup directory remains runtime data and must stay ignored.

### 7.4 Logging

Add log types:

- `report_delete`
- `storage_migration`
- `quote_override`
- `report_asset_link`

Keep log rows compact; do not log full report HTML or personal sensitive content.

## 8. Testing Strategy

### Unit Tests

Use `node --test`.

Add tests for:

- `deleteReport` normal path.
- `deleteReport` with missing file.
- `deleteReport` not found.
- report deletion path traversal rejection.
- Today history excludes archived reports.
- status date contract.
- Settings LLM status comes from backend settings/status payload.
- schedule/task executable filtering from a single backend source.
- hash query parsing/building for Knowledge search.
- quote override fallback through backend quote lookup.
- decision market fallback when live cache is empty.
- report-asset link format and query.

### Integration Tests

Prefer handler-level or Module-level tests without starting full HTTP server initially.

Storage migration tests:

- Create temp DB.
- Insert sample reports/settings/tasks.
- Reopen DB.
- Verify data persists.
- Verify transaction rollback.
- Verify `undefined -> null`, boolean parameter normalization, and `.changes` return contract.

### Frontend Logic Tests

Keep pure functions in `src/lib` tested.

If adding URL/hash parsing for Knowledge search, put parsing/building in a pure helper and test it.

### Build Verification

Every milestone must pass:

```bash
npm test
npm run build
```

Additional v0.4 storage migration Gate:

```bash
docker compose up -d --build
```

The storage migration is not complete until a container starts successfully and a copy of the existing `data/app.db` can run through key read/write paths.

## 10. Migration and Compatibility

- Existing `data/app.db` should remain the source of truth.
- No report HTML path format change in v0.3/v0.4.
- Keep `now` field in `/api/status` for one release while adding `today/nowIso/nowDisplay`.
- Keep old tasks in DB even if UI hides custom creation.
- Avoid changing import report JSON contract.

## 11. Security and Data Boundary

- Do not commit `data/`, DB backups, report HTML, personal holdings, logs, API keys, cookies or tokens.
- Export endpoints require authenticated session.
- Import token logic remains unchanged.
- Delete/export actions must not expose secrets from settings or environment variables.
- Report deletion should only delete paths resolved under `REPORT_DIR`; never accept raw file paths from client.

## 12. Open Decisions

1. 报告删除是否需要“撤销”窗口？建议先不做，保留确认即可。
2. 自定义任务已有数据是否在 UI 中展示为“规划中”？建议如果 DB 中已有，则折叠展示，避免用户以为数据丢失。
3. 搜索跳转前如何保护当前页面未保存输入？建议 v0.3 先做到非空搜索才跳转，复杂脏表单提示留后续评估。
4. report-asset link 是否自动识别股票代码？建议先手动 + 简单 tag 提示，避免误关联。
5. 暗色模式是否进入 v0.6？建议作为 spike，不阻塞维护性改造。
