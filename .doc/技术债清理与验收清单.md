## 分类一：未完全兑现的功能（本轮修复）

### F1 报告删除缺少事务原子性

- **现状**：`server/routes/reports.js:72-81` 的 `deleteReport` 把「删资产链 / 删报告行 / 写日志」拆成三个独立写操作，无事务包裹。
- **原因**：技术设计文档 §7.2 明写「到 v0.4（better-sqlite3）后，DB 删 + 日志入一个 transaction」。现已在 better-sqlite3 上、`db.transaction` 也已验证可回滚（`server/services/db.test.js:24`），却未使用。任一步抛错会留下「资产链已删但报告还在」的中间态。
- **目标**：DB 侧三步（删资产链、删报告行、写日志）在一个 `db.transaction` 内全成或全败；文件删除不可回滚，保持在事务外、先于事务执行（当前顺序正确，予以保留）。
- **验收标准**：
  - [ ] `deleteReport` 内部使用 `db.transaction` 包裹 DB 写操作。
  - [ ] 新增测试：事务内 DB 删除抛错时，报告行与资产链均回滚（不出现半删）。
  - [ ] 既有 3 条删除测试（正常 / 文件缺失 / 不存在 / 越界路径）仍全绿。
  - [ ] 返回契约不变：`{ deleted: true, fileDeleted: boolean }`。

### F2 自动关联把任意 6 位数字误判为标的

- **现状**：`server/routes/report-assets.js:131` 对正则匹配到的每个 6 位数字都建 `mentioned` 链接——`knownAssets.get(code) || { code, name:"", market:"" }` 的兜底分支让**未知数字也入库**。`getReportAssetLinks` 不校验 code 真实性，ReportReader「相关标的」会显示幽灵条目。
- **原因**：需求文档 Open Decision 4 明确要求「先手动 + 简单 tag 提示，**避免误关联**」。当前实现把「300000 元」「600000 万」这类正文数字也关联成标的，直接违背该决策。
- **目标**：raw 6 位数字路径**只对已知资产（positions/stocks/quote_overrides 中存在的 code）建链**；未知数字不自动关联。已知名称匹配路径（`report-assets.js:135-137`）本就安全，保留。手动关联（`upsertReportAssetLink`）不受影响，用户仍可手工加任意代码。
- **验收标准**：
  - [ ] `extractAssetHints` 对未在 knownAssets 中的 6 位数字不产生 auto 链接。
  - [ ] 新增测试：含未知代码 + 无关数字的报告，auto 链接数为 0（或仅命中已知资产）。
  - [ ] 既有「代码 + 已知名称命中」自动建链测试仍绿（`report-assets.test.js:47`）。
  - [ ] 手动关联能力不受影响（`upsertReportAssetLink` 仍可加任意 code）。

### F3 决策页仍自行计算「今日」，未复用 status.today

- **现状**：`src/pages/Decisions.jsx:16` 用 `new Date().toLocaleDateString("en-CA", { timeZone })` 本地算日期，而 `Today.jsx:38`（`s?.today`）、`Signals.jsx:8`（`status.value?.today || localToday()`）已统一走后端字段。
- **原因**：v0.4 改造目标是「消除前端各自算日期、统一 `/api/status` 结构化字段」。Decisions 是漏网页面，形成三页两套口径，后端调整日期定义时会独立偏移。
- **目标**：Decisions 复用 `status.value?.today`，与另两页对齐；保留本地兜底避免 status 未加载时空白。
- **验收标准**：
  - [ ] `Decisions.jsx` 的 `today` 优先取 `status.value?.today`。
  - [ ] `status` 未就绪时有本地兜底，不崩、不显示空日期。
  - [ ] `npm run build` 通过。

### F4 version 字段停留在 0.2.0

- **现状**：`package.json:3` 与 `server/routes/reports.js:30` 的 `getStatus` 都返回 `version: "0.2.0"`，但已迭代至 v0.6。
- **原因**：`/api/status` 把 version 透出给前端（设置页/调试用），提交在讲 v0.3–v0.6、代码版本号不动会误导。
- **目标**：统一 bump 至 `0.7.0`（本轮清理版本），两处保持一致，消除硬编码漂移。
- **验收标准**：
  - [ ] `package.json` version = `0.7.0`。
  - [ ] `getStatus` 返回的 version 与 `package.json` 一致（理想做法：读取 package.json，不再硬编码）。
  - [ ] `npm test` / `npm run build` 通过。

## 分类二：防止腐化的架构优化（本轮落档，后续里程碑执行）

> 依据 AGENTS.md：架构清理不以「也能工作」为目标，应追求清晰、优雅、可扩展的模块边界与数据流。以下三项是技术设计文档已规划、但迭代中「升级点已越过却未执行」的债务。

### A1 `server/index.js` 仍是 god-file，报告构建逻辑未归位

- **现状**：`server/index.js` 约 460 行，同时承担路由分发 + 报告构建 + 日更编排。技术文档 §3.2 规划的 Report Lifecycle Module 只做了一半：`report-file-store.js` 抽得干净到位，但 `report-writer.js` 只是 3 行薄壳，真正的 `createReport` / `importReport` / `createDailyMarketBriefReport`（约 200 行）仍留在 `index.js`。
- **原因**：违背 §3.2「ReportWriter 负责创建/导入报告」的模块边界；报告构建与 HTTP 分发耦合在一个文件，Locality 差、难独立测试。
- **目标**：将三段报告构建逻辑迁入 `report-writer.js`（或新 `server/services/report-lifecycle.js`），`index.js` 回归纯路由分发；迁移后删除 index.js 内的相关私有函数，不留双份（遵守 AGENTS.md「及时删旧路径」）。
- **验收标准**：
  - [ ] `createReport` / `importReport` / `createDailyMarketBriefReport` 不再定义在 `server/index.js`。
  - [ ] 报告构建模块可被单测直接 import（新增至少 1 条构建/落盘路径测试）。
  - [ ] `index.js` 行数显著下降（目标 < 300 行）。
  - [ ] `npm test` / `npm run build` / 起服务 + 生成报告冒烟通过。

### A2 HTTP 路由仍是手写 if/regex 长链，未引入路由表

- **现状**：`handleApi` 在 v0.5/v0.6 新增 assets/quotes/overrides/export 约 15 个分支后进一步变长，接近不可维护。
- **原因**：技术文档 §7.1 定义的升级点是「v0.4/v0.6 引入极简 route table（method+pattern→handler）」，现已越过 v0.6 仍未做，分支持续膨胀，与 AGENTS.md「避免腐化」冲突。
- **目标**：引入 `[{ method, pattern, handler }]` 声明式路由表，`handleApi` 变为「查表 + 派发」；auth gate 作为表项属性或前置中间件保留（不得降低现有鉴权覆盖）。
- **验收标准**：
  - [ ] 路由以数据表声明，新增 API 不再往 `handleApi` 追加 if 分支。
  - [ ] 鉴权边界不变：公开端点（session/login/logout/import）与受保护端点划分与现状一致。
  - [ ] handler 可独立单测。
  - [ ] 全部现有 API 行为不回归（`npm test` + 关键路由冒烟）。

### A3 自动关联每次插入报告都全表重查已知资产

- **现状**：`syncAutoReportAssetLinks` → `getKnownAssets`（`report-assets.js:142`）每次 `insertReport` 都查 positions + stocks + quote_overrides 三张表。
- **原因**：日更 / 批量导入时是 N× 冗余查询，属可预见的隐性成本（个人数据量下暂无感，但结构不干净）。
- **目标**：按需缓存 knownAssets（进程内带失效），或将关联同步改为批量导入后一次性执行，减少重复查询。
- **验收标准**：
  - [ ] 单次批量导入 N 篇报告时，已知资产查询次数不随 N 线性增长（或有明确缓存/批处理边界）。
  - [ ] 自动/手动关联结果与现状一致（既有 report-assets 测试全绿）。
