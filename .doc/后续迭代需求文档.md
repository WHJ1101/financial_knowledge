# Financial Knowledge 后续迭代需求文档

> 日期：2026-07-02
> 来源：`.doc/项目评审报告.md`
> 范围：围绕个人 AI 投研工作台的核心体验、产品边界、数据可靠性和可维护性做连续迭代
> 目标版本建议：v0.3 至 v0.6

---

## 1. Problem Statement

Financial Knowledge 已经具备个人投研工作台的基本形态：报告沉淀、今日入口、持仓/自选、信号源、每日简报、任务调度和设置。当前最大问题不是基础能力不足，而是产品能力与呈现不完全匹配、核心知识库操作闭环缺失，以及部分技术实现限制了后续扩展。

从用户视角看，主要痛点是：

- 想清理错误或过期报告时，只能归档，不能删除。
- 在顶栏搜索报告时，如果当前不在报告列表页，搜索没有可见反馈。
- 任务页允许创建任意任务，但实际只有每日简报能执行，容易误判系统能力。
- README 仍描述独立行情页，但产品入口已经转为顶栏行情和投资组合里的指数基金面板，文档与实际信息架构不一致。
- 持仓行情抓不到时，没有手动覆盖和导出兜底。
- 报告、持仓、自选之间缺少双向关联，投研结论难以沉淀成可复盘的决策链。
- 随着报告和日志增长，当前 sql.js 全量落盘会成为可靠性与性能瓶颈。

## 2. Product Positioning

本阶段继续坚持现有定位：**个人 AI 投研工作台，本地/单实例优先，围绕报告沉淀、持仓复核和每日决策辅助展开**。

产品不应扩张成通用自动化 Agent 平台。任务系统在没有多个可执行器之前，应以“内置投研自动化配置”为主，而不是自由创建任意任务。

## 3. Solution

后续迭代采用“四段式”路线：

1. **v0.3 核心体验补齐**：补报告删除、用 hash query 修全局搜索、收敛任务页、同步 README 与导航口径，并修复今日历史归档过滤。
2. **v0.4 数据可靠性升级**：迁移到 better-sqlite3，提供真实事务、降低写放大，补结构化 today 字段，拆分前端按页加载，并由后端返回 LLM 配置状态。
3. **v0.5 投研闭环增强**：补手动行情覆盖、持仓/报告导出、报告与标的双向关联、持仓批量行情，并让决策页在行情缓存为空时有可靠回退。
4. **v0.6 可维护性与体验打磨**：拆分 Portfolio 视图、加 ErrorBoundary、统一删除确认、收敛内联样式、评估暗色模式。

## 4. Iteration Plan

| 版本 | 主题 | 目标 | 关键交付 |
|------|------|------|----------|
| v0.3 | 核心体验与产品边界 | 让用户能完成知识库基础管理，消除“看起来能用但实际不可用”的入口 | 报告删除、搜索 hash 恢复、任务页收敛、README 同步、今日归档过滤 |
| v0.4 | 数据可靠性与加载模型 | 解决存储上限和前端过度刷新，降低后续功能扩展成本 | better-sqlite3 迁移、真实事务、Docker 验证、按页加载、结构化 status、LLM 配置状态 |
| v0.5 | 投研工作流闭环 | 让报告、持仓、自选形成可复盘链路，并补行情兜底 | 手动行情覆盖、CSV/JSON 导出、报告-标的关联、批量报价、决策行情回退 |

## 5. User Stories

### v0.3 核心体验与产品边界

1. As a personal investor, I want to delete a wrong report, so that my knowledge base does not keep misleading material.
2. As a personal investor, I want report deletion to remove both metadata and the generated HTML file, so that deleted content does not remain accessible by stale links.
3. As a cautious user, I want a confirmation step before deleting a report, so that I do not accidentally lose useful research.
4. As a report reader, I want to delete a report from the reader page, so that I can clean up bad reports while reading them.
5. As a knowledge base user, I want to delete reports from the report list, so that batch review and cleanup are efficient.
6. As a user searching from the top bar, I want search results to be visible regardless of my current page, so that typing a query never feels ignored.
7. As a user on the portfolio page, I want a top-bar report search to take me to the knowledge base results, so that I can immediately inspect matching reports.
8. As a knowledge base user, I want search, topic, origin, starred, archived filters to work together, so that I can narrow down research quickly.
9. As a user, I want the task page to show only actually executable automations, so that I understand what the system can run.
10. As a user, I want the daily briefing task to expose clear enable/disable and schedule controls, so that I can manage daily automation confidently.
11. As a user, I want unsupported custom automation tasks to be hidden or explicitly marked as unavailable, so that I do not create tasks that never execute.
12. As a maintainer, I want README navigation and feature tables to match the actual sidebar, so that future usage and deployment instructions stay trustworthy.
13. As a knowledge base user, I want archived reports to disappear from Today history, so that archive behavior is consistent across entry points.

### v0.4 数据可靠性与加载模型

14. As a user with growing reports and logs, I want database writes to remain fast, so that the app does not degrade as data accumulates.
15. As a maintainer, I want real SQLite transactions, so that multi-step writes either complete together or fail together.
16. As a deployer, I want a safe migration path from the existing data/app.db, so that existing reports, tasks, settings and holdings are preserved.
17. As a deployer, I want Docker deployment to continue building and starting after the SQLite migration, so that production deployment remains reliable.
18. As a maintainer, I want the storage Interface to stay close to the current prepare/run/get/all usage, so that the migration has a small blast radius.
19. As a user navigating between pages, I want pages to load only the data they need, so that route changes feel quicker.
20. As a developer, I want each page's data dependencies to be explicit, so that future bugs are easier to localize.
21. As a frontend user, I want today-related views to use a structured date field, so that date display changes do not break filtering.
22. As a maintainer, I want status responses to include both display text and machine-readable dates, so that UI and logic are not coupled to Chinese-formatted strings.
23. As a user checking settings, I want LLM configuration status to reflect backend runtime configuration, so that the settings page does not mislead me.

### v0.5 投研工作流闭环

24. As a holder of funds or stocks, I want to manually override quote data when online sources fail, so that portfolio valuation remains usable.
25. As a portfolio user, I want manual quote overrides to show their source, so that I can distinguish live quotes from manual values.
26. As a user, I want to export holdings to CSV or JSON, so that my personal asset data is portable.
27. As a user, I want to export report metadata, so that I can backup or analyze my research library externally.
28. As a user reading a report, I want to see related holdings and watchlist items, so that I can connect research to decisions.
29. As a portfolio user, I want to see related reports from a holding detail panel, so that I can review the thesis behind a position.
30. As a user adding a report, I want tags or detected asset codes to create report-asset links, so that association is not entirely manual.
31. As a user, I want to manually add or remove report-asset links, so that the knowledge graph stays accurate.
32. As a user with many holdings, I want portfolio quotes to load in batch, so that the portfolio page does not wait on serial quote requests.
33. As a daily briefing user, I want decisions and reports to reference the same linked assets, so that daily guidance can be traced back to evidence.
34. As a decision-page user, I want market context to fall back to the latest available snapshot when live cache is empty, so that generated decisions do not degrade to “待接入” after restart or off-hours.

### v0.6 可维护性与专业体验

35. As a maintainer, I want Portfolio views split by tab, so that changes to positions, stocks, ETF mapping, and analysis are localized.
36. As a maintainer, I want pure calculation Modules to remain tested independently, so that visual refactors do not break portfolio math.
37. As a user, I want a graceful error state instead of a blank screen, so that one render bug does not block the whole app.
38. As a user, I want destructive actions to use consistent confirmations, so that delete/archive behavior is predictable.
39. As a frontend maintainer, I want inline styles moved to named classes, so that design changes remain centralized.
40. As a heavy reader, I want a future dark mode option, so that the app is more comfortable for long reading and market monitoring sessions.

## 6. Functional Requirements

### FR-1 报告删除

- 知识库列表和报告阅读页提供删除入口。
- 删除前必须二次确认。
- 删除成功后，报告列表立即刷新。
- 删除应同时清理 reports 表记录和磁盘 HTML 文件。
- 如果 HTML 文件已经不存在，删除元数据仍应成功，并记录降级信息。

### FR-2 全局搜索结果落地

- 顶栏搜索输入后，应将用户带到知识库页面或搜索结果视图。
- 搜索词必须保留在 URL hash query 中，刷新页面后可恢复。
- 搜索结果为空时显示明确空态。
- 搜索应与知识库筛选条件组合生效。
- 搜索跳转前应尽量避免丢失当前页面未保存输入；若当前页面有未保存表单，至少不应在空搜索或误触时跳转。

### FR-3 任务页收敛

- 任务页默认只展示实际可执行的内置自动化任务。
- 每日简报任务支持开启、暂停、修改执行时间、立即执行、查看最近日志。
- 自定义任务创建入口在没有执行器注册机制前不展示。
- 如果保留自定义任务数据，应标记为“规划中/不可执行”，不可误导用户。
- 前端应使用后端返回的 `executable` 字段，不再重复以名称正则判断任务是否可执行。

### FR-4 存储迁移

- 使用 better-sqlite3 替代 sql.js 全量落盘 wrapper。
- 保持现有数据文件可读，迁移前进行备份提示或自动备份。
- 提供真实 transaction。
- 保持现有路由和业务调用的行为不变。
- Adapter 必须保留当前参数归一化行为，包括 `undefined -> null`、布尔值转 `0/1`，并保留 `.run().changes` 返回契约。
- Docker Compose 构建和启动必须通过，不能只以本地测试和 Vite 构建作为迁移完成标准。

### FR-5 按页数据加载与结构化日期

- App 首次登录后只加载当前页面必要数据。
- 顶栏行情维持独立轮询。
- `/api/status` 返回 `today`、`nowIso`、`nowDisplay` 等结构化字段。
- Today 和 Signals 不再解析展示字符串。
- Settings 的 LLM 配置状态来自后端运行时配置，不再读取前端 `import.meta.env.VITE_LLM_API_URL`。

### FR-6 投研闭环增强

- 支持持仓手动行情覆盖，并显示数据来源。
- 支持持仓和报告元数据导出。
- 支持报告与持仓/自选双向关联。
- 支持持仓批量报价，减少 N+1 请求。
- 决策生成时如果实时行情缓存为空，应回退到最近可用行情或 `market_indices` 数据。

### FR-7 维护性与体验打磨

- 拆分 Portfolio 页面视图文件。
- 增加前端 ErrorBoundary。
- 删除、归档、移除等破坏性操作使用统一确认体验。
- 清理高频内联样式。

## 7. Non-Functional Requirements

- **数据安全**：继续遵守 `data/` 不入 Git，删除和导出功能不得泄露 API key、cookie、token。
- **单实例优先**：本阶段不追求多用户和水平扩展，但必须消除当前单实例内的写放大和假事务。
- **可回滚**：存储迁移必须能从备份恢复。
- **可测试**：核心业务变化必须有 node:test 覆盖；前端纯函数继续保持单测。
- **性能**：常规页面切换不应触发所有业务数据重拉；持仓报价应避免串行 N+1。
- **可访问性**：保留现有 aria、键盘操作、reduced motion 支持。

## 8. Acceptance Criteria

### v0.3

- 用户可以从知识库和报告阅读页删除报告。
- 删除后 DB 记录与 HTML 文件一致清理；不存在文件不阻塞删除。
- 在任意页面使用顶栏搜索后，能看到知识库搜索结果，且刷新后搜索词与结果可恢复。
- 任务页不再允许创建无法执行的自由任务。
- 今日页历史列表不展示已归档报告。
- README 功能表与实际导航一致。
- `npm test` 和 `npm run build` 通过。

### v0.4

- 应用使用 better-sqlite3 读写当前数据库。
- transaction 覆盖至少一个多写入场景。
- Adapter 参数归一化覆盖 `undefined` 和布尔值，`.run().changes` 返回契约保持可用。
- `docker compose up -d --build` 在迁移后能成功构建并启动。
- 页面切换不再统一调用全量 `refresh()`。
- `/api/status` 提供结构化日期字段。
- Settings 展示的 LLM 配置状态来自后端 status/settings。
- Today/Signals 日期逻辑不依赖 `split("·")`。
- `npm test` 和 `npm run build` 通过。

### v0.5

- 持仓可使用手动行情覆盖，并在 UI 中标出来源。
- 持仓和报告元数据可以导出为 CSV 或 JSON。
- 报告详情能看到相关标的，持仓/自选详情能看到相关报告。
- 多持仓报价改为批量或并发加载。
- 决策页市场环境在 live cache 为空时仍有最近可用数据回退。
- `npm test` 和 `npm run build` 通过。

### v0.6

- `Portfolio.jsx` 明显瘦身，Tab 视图分文件维护。
- 前端 render 异常显示可恢复错误页。
- 删除/归档/移除类操作确认体验一致。
- 高频内联样式迁移到 CSS class。
- `npm test` 和 `npm run build` 通过。

## 9. Implementation Decisions

- 先补齐用户可感知的 P0 体验，再处理存储迁移，避免一开始进入大改造。
- 任务系统短期收敛，不先建设通用任务平台。
- 存储迁移保留现有 `prepare/run/get/all` 调用习惯，减少改动面。
- 报告删除优先实现 DB + 文件双删；报告正文是否入库留到后续技术债处理。
- 全局搜索优先采用 `#knowledge?q=...` 的 hash query 跳转方案，不新增复杂搜索页。
- 投研闭环采用显式 report-asset link，再考虑自动识别。

## 10. Testing Decisions

- 报告删除测试应覆盖：正常删除、文件缺失但 DB 存在、报告不存在。
- 存储迁移测试应覆盖：读现有 schema、写入、事务回滚、settings JSON 读取、`undefined` 参数、布尔参数、`.changes` 返回。
- 日期结构化测试应覆盖：上海时区日期边界。
- 搜索测试应覆盖 hash query 解析、刷新恢复和清空搜索。
- 任务页测试重点在后端任务可执行性状态和前端展示逻辑。
- 报告-标的关联测试应覆盖双向查询。
- Portfolio 拆分后，保持 `portfolio-analysis` 和 `position-math` 的纯函数测试，不测试内部 UI 实现细节。

## 11. Out of Scope

- 多用户权限系统。
- 团队协作、评论、审批流。
- 通用 Agent 任务编排平台。
- 多实例水平扩展。
- 自动交易、下单、券商账户连接。
- 公开技能仓库同步或 Codex skills 内置化。

## 12. Risks

- better-sqlite3 涉及 native dependency，Dockerfile 必须同步补齐构建工具链或切换兼容基础镜像。
- 删除报告涉及不可逆数据变化，必须做好确认和备份说明。
- 搜索跳转如果处理不好，会打断当前页面未保存输入。
- report-asset 自动识别容易误关联，初期必须允许手动修正。
- 自定义任务收敛可能让已有数据“看起来消失”，需要迁移展示或说明。

## 13. Further Notes

本需求文档聚焦“个人可用、长期可维护”的迭代，不追求把产品扩成企业级投研平台。当前项目已有不少高质量基础：安全默认值、LLM 降级、报告模板兼容、纯函数单测。这些应继续保留，并作为后续改造的保护网。
