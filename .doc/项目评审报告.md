## 一、结论速览（TL;DR）

这是一个**完成度相当高、工程质量在个人项目里明显偏上**的 AI 投研工作台：安全护栏（无鉴权禁止对外监听）、纯函数抽离 + 单测、证据驱动的报告 pipeline、行情/基金多源兜底解析，这些都做得比一般 side project 认真。

核心问题不在"写得好不好"，而在**产品取舍与几个关键 Module 的 Depth 上限**：

1. **产品定位清晰，但功能面偏宽**——7 个一级页面对"个人单用户投研沉淀"这个场景来说偏重，决策/信号/任务三块存在能力与呈现不匹配（后端占位、前端已成型）。
2. **最大技术债是 `sql.js` 全量落盘存储**——每次写操作把整个数据库 `writeFileSync` 到磁盘，且 README 明说"不支持多进程并发写入"。这是整个架构可扩展性的硬上限。
3. **前端设计语言统一、克制、专业**，A 股红涨绿跌、tabular-nums、响应式断点都到位；主要短板是**信息架构的重复**（顶栏全局搜索与知识库筛选割裂、数据重复加载）。

下面分层展开。

## 二、产品层面

### 2.1 产品定位是否清晰 —— ✅ 清晰

定位非常明确且自洽：**个人 AI 投研工作台，本地/单实例优先**。README、AGENTS.md、代码内注释三处口径一致：

- 沉淀"定时任务 / 网页按钮 / Codex 对话"三种来源的投研报告（`origin: automation | manual`）；
- 结合行情、自选股、持仓做决策辅助；
- 明确"云端跨设备靠同一部署实例，不靠 Git 同步 `data/`"。

定位没有摇摆，这是加分项。**唯一的定位模糊点**：它到底是"报告阅读器 + 轻量持仓管理"，还是"自动化投研 Agent 平台"？当前实现更偏前者（真正能自动跑的只有"每日市场简报"一个任务），但"任务"页的 UI 却暗示后者（可自由创建任意任务）。这个预期差需要产品上收敛（见 2.3）。

### 2.2 产品功能是否混乱 —— ⚠️ 不混乱，但有"能力/呈现错配"

整体功能组织是清楚的，7 个主页面各有主题。但有三处**前端呈现的完整度 > 后端能力的完整度**，会让用户产生"这功能是不是坏了"的困惑：

| 页面 | 前端呈现 | 后端真实能力 | 错配风险 |
|------|---------|-------------|---------|
| 任务 | 可自由填写"名称/目标/执行方式/时间"创建任意任务 | 只有 `daily-research` 一个任务有执行器，其余创建后调度器只写日志"No executor configured"（`server/index.js:283`），静默失效 | 高：用户建的任务不会跑，也没有明显反馈 |
| 决策 | "市场环境"整块展示 | 数据来自 `getMarketData()` 内存缓存（`decisions.js:16`），非交易时段/刚启动时为空，落为"待接入" | 中：决策质量随启动时机波动 |
| 信号源 | 4 个指标卡 + 信号池 + "同步飞书"按钮 | 需要 `FEISHU_APP_ID/SECRET` + wiki url，未配置时同步直接 `skipped`（`communitySignalPipeline.js:19`） | 中：空态文案有引导，但按钮点了"没反应"体验差 |

**建议**：对"尚未真正打通"的能力，前端要么隐藏、要么显式标注"需配置 X 才能启用"，而不是给一个看起来可用、点下去无声失败的入口。

### 2.3 有哪些不必要的功能 —— 建议收敛

以"个人单用户 + 单实例"这个已确立的定位为尺子：

1. **通用"任务创建"表单（强烈建议移除或改造）**
   `Tasks.jsx` 的自由建任务表单是"伪功能"：后端无对应执行器。要么删掉表单只保留"每日简报"这一个内置任务的开关/改时间；要么把它明确降级为"占位/规划",并在 UI 标注"实现待接入"。当前状态是最差的——看起来能用。

2. **"归档"与"标星"并存，但归档缺少独立视图闭环**
   `ReportList` 里标星（★）和归档（📦）两个按钮并列，但归档后只能在知识库切到"归档"tab 才看得到，且今日/历史列表不区分归档态（`Today.jsx` 的历史列表 `slice(0,20)` 不过滤 archived）。功能不算多余，但**语义重叠**（标星=重要，归档=不重要收起来），个人场景下二选一即可。

3. **决策页"历史决策"折叠列表**
   每天一条、去重保留最新——对个人用户，历史决策的复看价值有限，且和"报告"存在信息重叠（决策本质是当天报告+持仓的聚合）。可考虑并入今日页的一个模块，减少一个一级导航。

> 不建议粗暴删除，但**7 个一级页面 → 5~6 个**会让产品更聚焦：今日、知识库、投资组合、（可选）信号、设置。决策并入今日，任务并入设置。

### 2.4 有哪些必要但缺失的功能 —— 关键补齐项

按对"投研沉淀"价值排序：

1. **报告的删除 / 手动纠错（P0）**
   目前报告只能标星、归档、标已读，**没有删除**。自动日更 + 手动导入会持续堆积（磁盘已有 50 篇 HTML），错误报告无法清理。个人知识库没有"删"是硬缺陷。

2. **全局搜索的结果落地页（P0）**
   顶栏搜索框驱动 `query` signal → `loadReports`，但**搜索结果只在当前所在页的报告列表里生效**。在"投资组合"页打字搜"光模块"，用户看不到任何反馈（该页不渲染报告列表）。搜索应有独立结果视图或至少自动跳转到知识库。

3. **持仓的手动行情覆盖 / 数据导出（P1）**
   持仓行情靠东财/腾讯/天天基金多源抓取，抓不到就"无行情"。缺一个手动录入现价的兜底，以及持仓/报告的导出（CSV/JSON），个人资产数据应可带走。

4. **报告与持仓/自选的双向关联（P1）**
   决策里有"关联报告",但报告详情页看不到"关联到哪些持仓/自选"。投研的核心价值是"标的↔观点"闭环，目前是单向的。

5. **移动端登录态与错误边界（P2）**
   `App` 顶层无 ErrorBoundary，任一页 render 抛错会白屏（这与全局 CLAUDE.md 强调的"JSX 运行时后验"呼应——运行时未定义引用只在渲染到才炸）。

## 三、技术层面

### 3.1 前端

#### 3.1.1 设计风格 —— ✅ 优雅、专业、符合业界标准

`src/styles.css`（626 行，手写、无 UI 框架）质量很高：

- **设计 token 化**：`:root` 统一 `--bg/--ink/--accent/--green/--red/--line/--shadow`，色板克制专业。
- **A 股本地化正确**：红涨绿跌（`.money-up{color:red}` / `.money-down{color:green}`），`font-variant-numeric: tabular-nums` 保证数字对齐——这是投研工具的专业细节。
- **响应式完整**：1100 / 860 / 520 三档断点，侧边栏在窄屏转横向滚动条，顶栏行情条 grid 重排，考虑周到。
- **可访问性有意识**：`aria-label`、`role="tablist"`、`prefers-reduced-motion` 下关闭打字机/骨架动画（`Portfolio.jsx:966`、`styles.css:505`）——超出一般项目水准。
- **微交互到位**：AI 分析的骨架屏 + 打字机效果（`TypewriterField` 用 `Intl.Segmenter` 按字素切分，中文友好）。

**可改进点（非硬伤）**：
- 大量内联 `style="..."` 散落在 JSX（`Decisions.jsx`、`Today.jsx`、`ReportList.jsx`），与 CSS 文件的 token 化风格不统一，建议收进 class。
- 颜色语义在 `report.js` 模板里又重定义了一套（`--good:#dc2626` 表示涨），与主站 CSS 变量命名"good/bad"含义相反，跨文件阅读易混淆。
- 无暗色模式（`color-scheme: light` 写死）——投研盯盘场景暗色需求较高，可作为增强项。

#### 3.1.2 页面拆分 —— ✅ 基本合理，一处过大

页面按业务域拆分清晰：`Today / Knowledge / Signals / Portfolio / Decisions / Tasks / Settings`，路由用 hash 简单可靠。纯计算逻辑已抽到 `src/lib/`（`portfolio-analysis.js`、`position-math.js`、`format.js`）并配单测——**这是本项目工程性最强的部分**，值得肯定。

**唯一问题：`Portfolio.jsx` 单文件 1026 行**，内含 20+ 个组件（面板、表格、详情、图表、打字机…）。虽然逻辑已外置，但视图组件仍应按 Tab 拆分为 `PositionPanel.jsx / AnalysisPanel.jsx / StockPanel.jsx / EtfPanel.jsx`。当前体量对维护和 code review 都偏重。

#### 3.1.3 侧边栏 / 顶栏 / 页面按钮 —— ⚠️ 结构合理，但有重复与遗留

- **侧边栏**（`Sidebar.jsx`）：手写 SVG 图标、active 态、窄屏横向滚动——干净。`NAV` 当前为 7 项，已经没有 `#market` 入口；但 `README.md` 的功能表仍列出"行情"页，而 `src/pages/Market.jsx` 已删除。这里不是死链问题，而是**产品信息架构与文档未同步**：需要确认"独立行情页"是否已被顶栏行情 + 投资组合 ETF 面板替代。

### 3.2 架构层面

#### 3.2.1 代码实现是否清晰、合理 —— ✅ 总体清晰，细节有坑

**做得好的：**
- **LLM 客户端收敛**（`lib/llmClient.js`）：注释明说"之前三处各自重复实现，这里收敛"，env 解析优先级（`FINANCE_KNOWLEDGE_* > LLM_* > OPENAI_*`）清晰，JSON 容错解析（去代码围栏 + 截取首个 `{}`）实用。
- **鉴权安全护栏**（`server/index.js:33` `assertHostIsSafe`）：无鉴权时拒绝对外监听，需显式 `ALLOW_INSECURE_HOST` 绕过——安全意识到位。HMAC 签名 session、`timingSafeEqual` 防时序攻击（`auth.js`）都规范。
- **研究 pipeline 分层**（`researchPipeline.js`）：证据采集（本地文件/HTTP/历史报告）→ LLM → 降级草稿，LLM 失败有 `buildEvidenceBasedDraft` 兜底，不会白屏。prompt 里明确"只输出结论不复制证据表格"，工程约束清楚。
- **测试覆盖**：47 例覆盖了 schedule 解析、报告模板渲染、持仓数学、组合分析等纯逻辑——正是最该测的部分。

**主要问题：**

1. **【P0】`sql.js` 全量落盘是性能与并发的硬伤**（`server/services/db.js:53`）
   `saveDb()` = `writeFileSync(DB_PATH, db.export())`，而它被挂在**每一次 `prepare().run()` 之后**。这意味着：
   - 每写一条日志（`appendLog` 被大量调用）就把**整个数据库序列化写盘一次**；
   - `transaction()` 是假的（注释也承认"sql.js 不支持显式事务，直接跑，每次 run 已落盘"），没有原子性；
   - README 已承认"不支持多进程并发写入"。
   数据量小时无感，但报告/日志累积后，写放大会线性恶化，且市场轮询 + 调度器 + 请求处理三个写入方并发时有**数据竞争与写覆盖风险**。这是"能跑但不可扩展"的典型。**建议**：迁移到 `better-sqlite3`（真事务、增量写、WAL），API 几乎兼容（现有 wrapper 就是模仿它的）。

2. **【P1】前端数据重复加载**
   `refresh()`（`store.js:17`）= status + reports + business + market 四把全量拉取，而 `loadBusiness` 里已经拉了 signals，`Signals.jsx` 挂载又走 `refresh` → 再拉一次；`App` 每次路由变化（非报告页）都 `refresh()`（`app.jsx:32`），意味着切到"设置"页也会重拉持仓/信号/日志。**过度获取**，应按页面懒加载所需数据。

3. **【P1】"今日"日期靠解析中文字符串**
   `Today.jsx:38` / `Signals.jsx:8`：`s?.now?.split("·")[1]?.trim()?.split(" ")[0]`——从 `周一 · 2026-07-01 ...` 里切日期。`lib/datetime.js` 已经有 `localDate()`，前端却去解析后端拼好的展示字符串。格式一变就静默出错，是脆弱耦合。应让 `/api/status` 直接返回结构化 `today` 字段。

4. **【P2】持仓行情 N+1 拉取**（`Portfolio.jsx:129`）
   `for (const p of items)` 串行 `await`，每个持仓最多 2 个请求（先 quote 再 search 再 quote）。持仓多时首屏慢。可 `Promise.all` 并发 + 后端批量报价接口。

5. **【P2】报告"存在性"用文件系统兜底**（`reports.js:113` `reportFileExists`）
   DB 与磁盘 HTML 双写，读取时反复 `existsSync` 校验、还有 `findReplacementReport` 找替身。这是双写不一致的补丁式修复。根因是"报告正文存文件、元数据存 DB"的割裂。数据量不大时可考虑正文也入库（或对象存储），去掉这层脆弱校验。

#### 3.2.2 架构设计是否可兼容可扩展 —— ⚠️ 单机可用，扩展性受限

**可扩展的部分：**
- **路由/服务/pipeline 三层分离**清楚，加一个新报告类型（`REPORT_TYPES`）、新数据源（`data/sources/*.json` 自动采集）成本低。
- **LLM 供应商可换**（OpenAI 兼容 + env 覆盖），换模型/自建网关无需改代码。
- **新闻源可插拔**（`dailyMarketBriefingPipeline` 的 `newsProviders` 数组，东财/GDELT/自定义 URL 可开关）。

**扩展性天花板：**
1. **存储层**（如上，`sql.js` 单文件全量落盘）——**这是第一个会撞墙的地方**，任何"多用户/多进程/高频写入"都走不通。这是架构级而非实现级问题。
2. **单进程内存状态**：市场缓存、调度器 `running` 锁都是模块级变量，天然无法水平扩展。定位是"单实例"所以当前合理，但一旦要多副本就得引入外部缓存/锁。
3. **任务系统是硬编码而非可扩展框架**：`isDailyMarketBriefingTask` 用正则匹配任务名来路由执行器（`server/index.js:371`），加新任务类型要改核心分发逻辑，没有"任务类型→执行器"的注册表。与前端"自由建任务"的开放感不匹配。
4. **HTTP 层是手写 `if/regex` 路由**（`server/index.js` `handleApi` 一长串 `p.match(...)`）：轻量够用，但已接近可维护上限（~90 行分支）。再加功能建议引入极简路由表（method+pattern→handler 映射），否则分支会继续膨胀。

**兼容性：**
- 向后兼容做得不错：DB 用 `IF NOT EXISTS` + 容错 `ALTER TABLE`（`db.js:44`）平滑加列；报告模板有 `modernizeReportHtml` 把旧 HTML 升级渲染。这说明作者有演进意识。

### 3.3 架构 Deepening Opportunities

这里用 Module / Interface / Implementation / Depth / Seam / Adapter / Leverage / Locality 这套词来描述后续重构机会。核心判断来自 Deletion test：删掉这个 Module 后，复杂度是消失了，还是会重新散落到多个调用方。

1. **存储 Module：把 `sql.js` wrapper 换成真正的 SQLite Adapter**
   - **Files**：`server/services/db.js`、所有 `db.prepare(...).run/get/all` 调用点。
   - **Problem**：当前 Interface 模仿 `better-sqlite3`，但 Implementation 是 sql.js 内存库 + 每次写入全量 `db.export()`。这个 Interface 看似小，实际把"无真事务、写放大、单进程"这些调用方必须知道的事实藏起来，Depth 不够。
   - **Solution**：保留现有 `prepare/run/get/all/transaction` Interface，替换底层 Adapter 为 `better-sqlite3`；迁移后让 `transaction` 成为真实事务，并把写盘交给 SQLite WAL。
   - **Benefits**：调用方获得更高 Leverage（不用理解落盘细节），维护者获得更好 Locality（存储一致性集中在一个 Module），测试也能围绕同一个 Interface 做内存/文件两类 Adapter。

2. **报告生产 Module：从 `server/index.js` 拆出报告写入与日更编排**
   - **Files**：`server/index.js` 的 `createReport`、`importReport`、`runDailyJob`、`createDailyMarketBriefReport`，以及 `server/routes/reports.js`。
   - **Problem**：HTTP 分发 Module 同时承担鉴权、文件服务、报告生成、导入、日更、信号同步。它的 Interface 是整条请求路径，Implementation 跨多个领域，属于 Shallow Module：理解一个接口要读很长的文件。
   - **Solution**：保留 `handleApi` 作为薄入口，把报告写入收成 `ReportWriter` Module，把日更收成 `DailyBriefingJob` Module；`server/index.js` 只在 Seam 处接收请求并调用明确 Interface。
   - **Benefits**：ReportWriter 的 Interface 可以统一处理"写 HTML + 写 DB + appendLog"这一组不变量，Locality 更强；后续补报告删除、报告正文入库或对象存储时，不需要继续扩张 `server/index.js`。

3. **任务执行 Module：让任务类型成为真实 Seam**
   - **Files**：`src/pages/Tasks.jsx`、`server/routes/tasks.js`、`server/index.js` 的 `runAutomationTask` / `isDailyMarketBriefingTask`。
   - **Problem**：前端 Interface 暗示用户能创建任意任务，但后端 Implementation 只有"每日市场简报"一个可执行路径；当前靠任务 id 或名称正则判断。按原则，One Adapter = hypothetical seam，这个 Seam 还没有真实成立。
   - **Solution**：产品上先收敛为内置任务配置；如果要开放任务，再引入 `task.type`，建立 `type -> executor` 注册表，至少有两个 Adapter 后再把它当成扩展 Seam。
   - **Benefits**：用户预期和系统能力对齐；任务新增的知识集中在执行 Module，获得 Locality；测试可以直接覆盖"未知 type 被拒绝/已知 type 执行"的 Interface。

4. **前端数据加载 Module：把全局 `refresh()` 拆成按页面需要的 Interface**
   - **Files**：`src/store.js`、`src/app.jsx`、各 `src/pages/*.jsx`。
   - **Problem**：`refresh()` 一次拉取 status、reports、business、market，路由切换时全量执行；页面对数据的真实需要被一个过宽 Interface 覆盖。Deletion test 下，删掉 `refresh()` 后复杂度会回到各页面，但也会暴露更准确的加载需求。
   - **Solution**：保留基础 signal store，但把 Interface 调整为 `loadTodayData`、`loadKnowledgeData`、`loadPortfolioData`、`loadTaskData` 等按页面组织的加载 Module；顶栏行情维持独立轮询。
   - **Benefits**：减少重复请求，提升首屏速度；每个页面的数据依赖更可读，Locality 更好；测试可以对页面加载 Interface 做契约验证。

5. **投资组合视图 Module：让 `Portfolio.jsx` 的视图拆分跟 `src/lib` 的计算拆分对齐**
   - **Files**：`src/pages/Portfolio.jsx`、`src/lib/portfolio-analysis.js`、`src/lib/position-math.js`。
   - **Problem**：计算 Implementation 已经抽到深 Module 并有单测，但视图 Implementation 仍集中在 1026 行文件里。Interface 不是错的，问题是维护者为了改一个 Tab 仍要穿过全部视图细节。
   - **Solution**：按 Tab 拆出 `PositionPanel`、`PortfolioAnalysisPanel`、`StockPanel`、`EtfPanel`，保留 `Portfolio.jsx` 作为编排 Module。
   - **Benefits**：视图变化的 Locality 明显提升；已有纯计算 Module 继续提供 Leverage；后续补持仓导出、批量报价、详情页编辑时更容易单点修改。
