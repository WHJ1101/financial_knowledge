## 一、结论速览（TL;DR）

这是一个**工程质量明显高于一般个人项目**的作品：后端分层干净、辩论引擎的并发/检查点处理扎实、前端设计系统（Liquid Glass 暖金）用心且无障碍到位。

核心问题不在"写得好不好"，而在**一次未完全收敛的产品转型**（个人单用户 → 小范围可信多用户）留下的三类欠债：

1. **定位口径未收敛**——README 说"多用户"，AGENTS.md 仍说"个人"，两份权威文档互相矛盾。
2. **迁移死代码**——整个宏观持久化子系统零写入/零引用，`akshare` 重依赖空耗。
3. **对 <10 人规模偏重的基础设施**——LangGraph 加密检查点、PG 队列、api/worker 分进程等生产级堆栈。

同时存在几个多用户定位下的功能缺口（用户管理 UI、改密）和一处会阻塞 API 的实现问题（`/jobs/daily`）。

> 本文档为一次性评审快照，用于对照后续迭代。落地优先级见文末第三节。

## 二、产品层面

### 2.1 产品定位 —— 当前清晰，但文档口径尚未收敛 ⚠️

项目经历过一次**根本性转向**（pivot），不是渐进漂移：

| 时期 | 定位 | 依据 |
|---|---|---|
| 旧 | 个人 AI 投研工作台，本地/单实例优先 | `.doc/项目评审报告.md`、`.doc/后续迭代需求文档.md` |
| 新 | 小范围可信多用户（<10 人）+ BYOK + 邀请码 | `README.md:3`、`.doc/投研工作台全栈重构技术方案.md` |

新版定位本身清晰自洽（README + 技术方案一致）。但存在两处未消解的矛盾：

1. **README 与 AGENTS.md 当前互相矛盾**：`README.md:3` 写"小范围可信多用户的 AI 投研工作台"，而根目录 `AGENTS.md:3` 第一句仍是"本项目是个人 AI 投研工作台"，且仍引用 `npm run report:import`、"Docker Compose 单机部署"等旧 Node 时代内容。AGENTS.md 只被部分更新。
2. **多用户体系是旧需求文档明确排除项**：`.doc/后续迭代需求文档.md` 的 Out of Scope 白纸黑字列出"多用户权限系统、团队协作、评论、审批流"，新方案却把"多用户 + 邀请码 + BYOK + 授权隔离"做成核心。这是主动翻案，不是自然演进。

**接手/评审提示**：以 `投研工作台全栈重构技术方案.md` 为唯一意图基线，旧三份文档仅作历史；把"多用户/BYOK/辩论"这条新增野心线，与"研报生产/行情/今日/任务"这条继承价值线分开评估。

**建议**：重写 AGENTS.md，删除 `report:import` 等旧路径描述，统一到多用户口径。

### 2.3 不必要的功能（建议收敛）

按"该删/该藏"排序：

1. **宏观持久化子系统是彻底的死代码（最该处理）**。`backend/app/models/macro.py` 的 `MacroSeries`/`MacroObservation` 两张表全项目**零写入**；`providers/akshare_macro.py` 的 `AksharesMacroProvider`、`to_orm_rows`、`providers/macro.py` 的通用 parser **零引用**（grep 确认）。真正跑的是 `eastmoney_macro.latest_macro_snapshot`（`instrument_evidence.py:136`）**每次实时联网抓取**，绕过整层表/Protocol。副作用：`akshare` 重依赖仅为死代码保留，且每场辩论都 N 倍冗余抓取全国唯一的宏观指标。
2. **旧决策归档**（`Decision` 模型 + `/decisions` 端点 + `useLegacyDecisions`）：只读、超管专属、复看价值低，是迁移包袱。
3. **对 <10 人偏重的基础设施**：LangGraph 加密检查点（`debate_runner.py:29-47`）、procrastinate PG 队列、api/worker 分进程、三密钥职责分离、Caddy 自动 TLS。技术方案 §16 自己也承认这层张力并降级了一批 SaaS 能力——但保留下来的仍是相当重的生产级堆栈，值得权衡投入产出比。

### 2.4 必要但缺失的功能（按价值排序）

1. **用户管理 UI（多用户定位下的硬缺口）**。`User.status` 有 `active|disabled`（`models/user.py:23`），但设置页只有邀请码管理（`SettingsPage.tsx:326` InviteSettings），没有成员列表、没有停用用户、没有改角色。超管发出邀请码后，无法看到谁注册了、无法踢人。
2. **改密/找回密码**：前端无任何入口（grep 无结果）。成员忘密码即无解。
3. **辩论标的受限**：`DecisionsPage.tsx:55-66` 的可选标的只来自持仓 + 自选，无法对任意标的直接发起辩论，得先加自选。对"投研决策"这个旗舰功能是明显约束。
4. **已知延后项**（技术方案 §16 承认）：SSE 实时推送（现为轮询）、审计日志 `audit_events`、BYOK 密钥轮换（仅留 `key_version` 字段）。

## 三、技术层面

### 3.1 前端

#### 3.1.1 设计风格 —— 优雅、专业、无障碍到位，是全项目亮点 ✅

- **设计系统成熟**：`styles/tokens.css`（532 行，亮/暗双主题）建立了完整的圆角层级（16/12/8px）、A 股红涨绿跌语义色（`--up/--down`）、Liquid Glass 折射材质，还附了详尽的"调参地图"注释。产品级而非 side-project 级的用心。
- **无障碍扎实**：`aria-*`/`role`/`sr-only` 普遍使用，且响应 `prefers-reduced-motion`、`prefers-reduced-transparency`、`forced-colors`（`app.css:1955/1984`）。这块做得比多数商业前端还好。
- **性能取舍聪明**：把操作层/侧栏的 `--glass-blur-md/lg` 压到 1px（`tokens.css:132`），避免大面积 backdrop-filter 的 GPU 开销；指针高光只写 CSS 变量、不触发 React 重渲染（`LiquidGlass.tsx:78`）。

安全细节：报告用 `iframe srcDoc` 渲染（`ReportReaderPage.tsx:197`），`sandbox="allow-same-origin allow-popups"`——**无 allow-scripts，脚本被禁**，加上后端 `_escape_html`（`report_lifecycle.py:319`），XSS 面可控。但 `allow-same-origin` 意味着导入的第三方报告 HTML 需保持可信来源。

#### 3.1.2 页面拆分 —— 合理，唯一冗余是持仓/自选两 tab 高度重复

- 路由全部 `lazy` 懒加载（`app.tsx:12-21`），hooks 按域拆分（9 个），组件抽取干净，**0 处内联 style**（grep 确认），有 `ErrorBoundary` 顶层兜底。
- `PortfolioPage.tsx`（450 行）内联 4 个子 tab——尚可接受，但 `PositionsTab` 与 `WatchlistTab` 的"添加表单 + 表格 + 详情面板"结构近乎重复，可抽公共骨架。

#### 3.1.3 侧边栏 / 顶栏 / 底部栏 / 按钮

- **侧边栏**（`SidebarNavigation.tsx`）：7 项 + 退出，带 Liquid Glass 滑动指示 pill，超管才显示"任务"（`app.tsx:77`）。桌面端优雅。
- **顶栏**（`MarketTicker.tsx`）：指数轮转 + 全局搜索 + 主题切换 + A/HK/US 开市点 + 时钟，信息密度高且克制。
- **底部栏**：无。**移动端是短板**——`app.css:805` 让侧栏在 <768px 变成横向 flex-wrap 行，7 个导航项换行会很局促。业界标准做法是底部 Tab Bar 或汉堡抽屉，这里的横向平铺换行偏简陋。
- **按钮**：统一 `GlassButton`（tone/size/state 三维，含 loading/success/error 态），一致性好。但删除/公开仍用原生 `window.confirm()`（`KnowledgePage.tsx:185/193`）——功能没问题，但与精致玻璃风不搭。

### 3.2 架构层面

#### 3.2.1 代码实现 —— 清晰，分层方向正确，主要问题是重复与死代码

**架构分层图（各层如何连接）**：

```
Caddy(前端/静态) ─► FastAPI(app/main.py, lifespan 起行情轮询)
                       │  api/ (15 路由) 依赖 core/auth 鉴权 + get_session
                       ▼
   services/ (23 文件) ── 业务编排 + 纯计算(pressure/portfolio_analysis)
       │           │                │
       ▼           ▼                ▼
  providers/    models/(ORM)   agents/decision(LangGraph 辩论图)
 (外部数据源)   SQLAlchemy 2.0       ▲ graph→roles→state
       │                            │
       └────────► llm/client(BYOK 路由) ─┘
                       │
        core/(auth/authz/crypto/security/ratelimit)

异步链路：worker.py ─► queue.py(procrastinate) ─► tasks.py ─► services/debate_runner|automation
```

依赖方向基本正确（services→api 0 处反向依赖、models 0 处上依赖、agents 纯净）。仅 2 处越界：`providers/community_signal.py:282` 反向 `from app.services.research import parse_llm_json`；`api/market.py:19` 直连 `providers.eastmoney`（跳过 service）。

**做得好**：
- 分层干净：`api→services→providers→models`，`agents/` 依赖注入可 fake 自验（`graph.py:23` ChatRouter Protocol、`roles.py:18` ChatFn Protocol）。
- **辩论引擎可靠性是全项目最强项**（`debate_runner.py`）：行锁保证"取消/完成只有一个终态胜出"（:147）、检查点续跑用无密钥快照对比（:111-113）、失败收敛先 `rollback()` 再锁行避免 `PendingRollbackError`（:176-178）、错误落库前正则脱敏 Bearer/sk-（:54-64）。
- **多租户隔离在查询层一致落实**：持仓/自选/辩论一律 `owner_id == user.id`；报告用 shared-OR-owner + 私有 404 不泄露存在性（`reports.py:93`）；BYOK 解析对 route 和 profile 双重 `user_id` 过滤，杜绝跨用户借用密钥（`llm/client.py:42-56`）。
- **BYOK/加密链路合规**：Fernet 加密落库、密文只出掩码（`crypto.py`）；SSRF 防护（https 强制 + host allowlist + DNS 解析后校验私有 IP）；密码 argon2；生产启动硬拒弱密钥（`config.py`）。

**问题**（按严重度）：

| 严重度 | 问题 | 位置 |
|---|---|---|
| 高 | 宏观死代码/废弃缓存层（见 2.3-1），拖着 akshare 重依赖 + N 倍冗余抓取 | `models/macro.py`、`providers/akshare_macro.py`、`providers/macro.py` |
| 中 | 长耗时日更 `await` 在 API 事件循环上跑同步 DB，会阻塞该 API 进程 | `api/jobs.py:94` `run_daily` |
| 中 | 三份重复的"从 LLM 输出抠 JSON"实现，容错行为已现细微差异 | `roles.py:24`、`research.py:189`、`llm/json.py` |
| 中 | provider 反向依赖 service（分层倒置） | `community_signal.py:282` |
| 中 | `_INDEX_SECIDS` 常量逐字节各写一份 | `eastmoney.py:463`、`daily_briefing.py:380` |
| 低 | `_save_report` 的 `brief` 形参从不使用 | `report_lifecycle.py:86` |
| 低 | 用户表 FK 的 ondelete 策略不一致（report/debate 无、其余 CASCADE/SET NULL） | `models/report.py:24`、`debate.py:31` |

#### 3.2.2 架构可扩展性 —— 数据源可扩展性好，辩论角色是主要债务点

- **加数据源（好）**：`providers/base.py` 有 Protocol + 携带 `source/retrieved_at/data_gap` 的快照 dataclass，各源独立、失败按 `data_gap` 降级——加一个行情源成本低。反例是宏观：`MacroDataProvider` Protocol 名存实亡。
- **加辩论角色（主要摩擦点）**：新增一个分析师面要同时改 4 处——`llm/context.py` 的 `AgentRole` Literal + `DEBATE_AGENT_ROLES`、`graph.py:20` 的 `_ANALYSTS` + `:135-147` 节点与边、`roles.py:40` 的 `ANALYST_PROMPTS` + schema、`state.py` 的 reducer。四处不同步就会静默漏跑或 KeyError。最该配置化的维度反而最分散。建议用一张角色注册表（role→prompt/schema/parallel-group）驱动。
- **多租户防御纵深不足**：隔离目前 100% 正确，但完全依赖开发者在每个 query 手写 `owner_id` 过滤，无 RLS、无统一 `scoped_query` 封装。新增端点一旦忘记过滤即数据泄漏，没有第二道防线。建议提供 `scoped_query(model, user)` 辅助或对隔离表启用 PostgreSQL RLS 兜底。
- **异步任务（好）**：procrastinate 同事务 `defer`（`scheduler_service.py:68`）模式统一正确，加新任务类型清晰。
- **god-object 核查**：点名的几个大文件（`daily_briefing` 473L / `research` 398L / `portfolio_analysis` 289L）绝大部分是内聚的纯函数流水线，非 god-object，拆分收益不大。`instrument_evidence.py`（310L）略杂（5 个证据面 + HTML 解析 + 内部 `asyncio.run`），是唯一值得考虑按证据面拆分的。
