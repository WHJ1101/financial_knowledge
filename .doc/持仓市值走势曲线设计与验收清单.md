# 持仓市值 / 盈亏走势曲线 设计与验收清单

> 日期：2026-07-09
> 需求来源：投资组合页面希望看到「持仓市值、盈利额、盈利率」的按天变化曲线，支持「最近半年」与「截至目前总共」两个时间范围。
> 方案：**为每只持仓回补历史收盘价 / 净值**，落 `daily_bars` 表，组合曲线**每次请求现算**（不落快照表），与既有「板块压力监控」保持同一数据哲学（见 `.doc/板块压力监控模块设计与验收清单.md` §3.2）。
> 验收基线：`npm test` 全绿（在现有基础上新增纯函数与路由用例）+ `npm run build` 通过 + 运行时后验冒烟。
> 数据源验证：本文所有接口 / 字段均于 2026-07-09 初测、2026-07-13 复测取到数（见「附录 A」）。
> 评审补齐：2026-07-10。已补充覆盖范围、基金日期时区、ETF 历史分页、复权口径、失败语义、手动回补、前端刷新和不完整数据展示规则。
> 口径修正（2026-07-13，结合 14 只真实持仓接口实测）：① ETF 改前复权 `fqt=1`（消除份额折算假暴跌）；② 基金改累计净值锚定前复权净值（消除分红假暴跌，且末点不虚高）；③ 基金归一化优先级写死、`market` 字段不可信需 pingzhongdata 兜底（防 LOF 同码错配）；④ range=all 成本基线随成分动态收敛（消除 −90% 假暴亏）。详见各节「实测更正」与附录 A。

## 一、背景与口径声明（务必先读）

### 1.1 需求

在「投资组合 → 组合分析」页新增一张全宽卡片，画三条按交易日变化的曲线：

1. **持仓市值**：组合每日总市值。
2. **盈利额**：组合每日浮动盈亏（¥）。
3. **盈利率**：组合每日浮动盈亏率（%）。

时间范围切换：**最近半年（约 126 交易日）** / **截至目前总共（当前数据源可回溯的最早日期至今）**。

### 1.2 【关键】口径限制——诚实披露

本项目**没有任何交易流水表**（无买入 / 卖出 / 加减仓记录，`positions` 表只存当前 `shares` 与 `cost`，已核对 `server/services/db.js:21` 及全库无 `transactions/trades/ledger` 类表）。因此历史某日的「真实持仓份额」无法重建。

本方案曲线的唯一可行、且诚实的口径是：

> **用「当前持仓结构」× 「历史价格」回溯合成**，即
> 某日市值 = Σᵢ∈S(t) (当前 sharesᵢ × 该日前复权价/前复权净值ᵢ)
> 某日盈亏 = 该日市值 − Σᵢ∈S(t) (当前 sharesᵢ × 当前 costᵢ)
> 某日盈亏率 = 该日盈亏 / 该日已入场成本 × 100%
>
> 其中 **S(t) = 截至 t 日已有价格数据的标的集合**（成分随历史逐日入场）。成本基线也必须随 S(t) 动态收敛，**市值分子与成本分母始终对同一集合**，否则出现假暴亏（见下）。

它表示「假设一直持有今天这套仓位，市值 / 盈亏会如何随行情波动」的回溯序列。**必须在 UI 上明确标注此口径**，避免误读为真实账户轨迹。若未来要真实历史，需新增交易流水表，属更大改造，不在本方案范围。

### 1.2.1 【关键】range=all 的成分分期入场问题（实测量化）

各标的历史深度差异极大——实测你的持仓最早 `163806` 可回溯到 **2008-11**，最晚 `025208` 才 **2025-09** 成立。`range=all` 从最早日画起时，早期只有个别标的有数据，会产生两类失真：

1. **市值阶梯**：市值随成分逐个"上市"阶梯式抬升，看似组合在增长，实则只是数据可得性在增加，是伪信号。
2. **盈亏假暴亏**（更严重）：若盈亏基线用**全量固定成本**，早期「少数标的市值 − 全部标的成本」会显示巨额假亏。实测（库内真实 shares/cost）：

   | 日期 | 已入场 | 已入场成本占全量 | 全量固定基线下的假盈亏率 |
   |---|---|---|---|
   | 2011-10 | 2/14 | 10.3% | **−89.7%** |
   | 2020-02 | 5/14 | 30.1% | **−69.9%** |
   | 2023-01 | 7/14 | 62.0% | **−38.0%** |
   | 2025-10 | 14/14 | 100% | 0%（成分集齐后才正常） |

**处置**：`buildPortfolioSeries` 的 `totalCost` 必须**逐日只累计 S(t) 内 hasCost 标的**（分子分母同集合，消除假暴亏，§4.2 已按此写）；这样盈亏率在早期反映的是"已入场部分"的真实盈亏，而非全组合。**但市值阶梯无法靠算法消除**——它是"成分未齐"的客观事实。故 `range=all` 必须：① 接口在 `coverage` 里返回**逐日成分覆盖数变化的最早"全成分齐备日" `fullCoverageSince`**；② 前端在该日之前的区间显式标注"成分未集齐，市值受标的上市先后影响"或灰显，**不得把 range=all 宣称为完整组合历史**。这条独立于 `syncStatus.truncatedSecids`（后者是分页截断，前者是成分入场）。

### 1.3 数据源实测结论（决定方案成立性）

- **A 股 / ETF 历史日线**：走东财 `push2his`，组合曲线与压力监控**统一使用前复权收盘价（`fqt=1`）**。**实测更正（2026-07-13）**：持仓的 `159995 芯片ETF华夏`（2026-07-07 份额折算）与 `588170 科创半导体ETF`（2026-07-06 折算）在 `fqt=0` 不复权序列上分别出现 **−50.1%**、**−66.7%** 的单日断崖，而 `fqt=1` 前复权序列同日基本持平（详见附录 A）。组合口径是「当前份额 × 历史价」，当前 `shares` 已是折算后份额，只有前复权价能与之匹配出连续市值，否则折算日会假暴跌。**两模块同用 `fqt=1` 后，`daily_bars` 同一 secid 不再有复权口径互相覆盖的隐患**（此前 fqt=0/fqt=1 混写会经 `INSERT OR REPLACE` 静默污染压力监控）。
- **场外基金历史净值**：走东财 `pingzhongdata/{code}.js`，**基于 `Data_ACWorthTrend`（累计净值）重构「前复权净值」序列，而非直接落累计净值原值**。**实测更正（2026-07-13）**：
  - ① 分红假暴跌：`163806 中银增利债券` 分红日（如 2015-12-17）单位净值 **−11.28%**，累计净值同日 **+0.13%**——单位净值把分红画成暴跌坑，必须用累计净值消除。
  - ② 但直接落累计净值原值会**市值虚高**：`163806` 当前单位净值 1.2417 / 累计净值 1.9299，用「当前份额 × 累计净值」算市值比真实市值（券商 APP 口径 = 份额 × 单位净值）**虚高 55.4%**，末点与 `getOverview` 概览、与成本口径全部错配（无分红的 `014662` 首末两序列相等、虚高 0%，问题只在分红基金暴露）。
  - ③ 正解与 ETF 前复权对称——锚定最新单位净值：`adjNav(t) = 最新单位净值 × 累计净值(t) / 最新累计净值`。缩放因子为常数，故日涨跌率 = 累计净值日涨跌率（消除分红假跌），且 `adjNav(最新) = 最新单位净值`（末点与概览/成本一致）。落库 `close` 存 `adjNav(t)`。
  - `Data_ACWorthTrend` 元素为 `[x(ms), y(累计净值)]` 二维数组；`Data_netWorthTrend`（`{x,y,equityReturn}`）用于取最新单位净值作锚点。按 `Asia/Shanghai` 转换、升序、去重。
- **历史深度边界**：ETF 接口按日期游标分页回补，直到返回条数小于分页大小或没有继续向前推进；查询层不使用 5000 条硬上限。基金接口返回的完整累计净值序列作为其数据起点。

## 二、架构与数据流

```
每日 runDailyJob（收盘后触发，跟随现有日更调度 15:30 Asia/Shanghai）
  └─ syncPortfolioBarsSafely()   ← 新增，try/catch 不阻断主流程（仿 runPressureMonitorSafely）
        ├─ getPositions() 读全部持仓
        ├─ 每仓 resolveBarSecid() 归一化出 daily_bars 的 secid（见 §三）
        ├─ A 股 / ETF → fetchHistoricalExchangeBars(secid, { adjustment: "qfq" })  前复权 fqt=1
        └─ 基金  → syncFundNavBars([code])           新增，抓 pingzhongdata 累计净值序列
                                                      → UPSERT 落 daily_bars（幂等）

前端 组合分析页 → GET /api/portfolio/history?range=6m|all
  └─ getPortfolioHistory()   ← 新增路由
        ├─ getPositions() 读当前持仓（shares / cost / secid）
        ├─ 每仓 getAllBars(secid) 取完整历史 close/nav
        ├─ buildPortfolioSeries() 纯函数：按 date 并集对齐 + 前值填充 + 加权合成
        └─ 返回 [{date, marketValue, pnl, pnlPct}] + meta（口径 / 覆盖率 / asOf / 缺数据标的）
```

### 2.1 核心设计决策（与压力监控一致）

- **`daily_bars` 是唯一存储，不新建快照表**：日线 / 净值是唯一需要持久化的原始数据；组合曲线是纯函数派生，请求时现算。避免「原始数据 + 派生序列」双份状态与同步问题，保持数据源单一。这与 `.doc/板块压力监控模块设计与验收清单.md` §3.2 决策一致。
- **基金净值也落 `daily_bars`**：复用同一张表、同一套 `getAllBars` 读取。基金无成交量，`volume` 记 `null`（与 VIX 一致）。落库的 `close` 为**累计净值**（见 §1.3），非单位净值。
- **本期支持范围**：人民币计价的 A 股、交易所 ETF 和场外基金。港股、美股及无法确认币种的持仓进入 `skipped`，不参与组合合成；后续增加币种与汇率字段后再扩展。
- **历史价格口径统一为前复权**：组合市值与压力监控都用 `fqt=1`。此前草案想让组合用 fqt=0、压力监控用 fqt=1「显式分离」，但 `daily_bars` 主键为 `(secid, date)`（`db.js:30`），同一 secid 两种复权口径经 `INSERT OR REPLACE` 会互相覆盖，无法真正分离；且 fqt=0 在折算日假暴跌（§1.3 实测）。统一 fqt=1 后既消除折算断崖，又消除主键冲突。
- **采集失败不阻断日更**：`syncPortfolioBarsSafely` 包 try/catch，异常仅 `appendLog`，不影响每日简报与压力监控。
- **回溯口径固定为「当前仓位 × 历史价格」**：见 §1.2，唯一可行口径，UI 必须标注。
- **不完整数据显式展示**：接口返回 `positionCoverage`、`costCoverage`、每标的 `firstDate`、`lastDate`、`staleDays`；覆盖不足时前端显示“覆盖范围内的回溯曲线”，不与全组合概览宣称完全对齐。

### 2.2 为什么挂进 `runDailyJob` 而非独立 automation task

`runAutomationTask`（`server/services/daily-job.js:46-50`）只对 `isDailyBriefingTask` 分派执行器，纯插一行 `automation_tasks` 不会被执行。搭现有日更车（在 `runDailyJob` 内加一步）改动最小、复用其 15:30 触发与当天幂等，与压力监控 `runPressureMonitorSafely` 完全同构。

## 三、secid 归一化（本方案最易错的一环）

`positions.quote_secid` 与 `daily_bars.secid` 需要按资产类型归一化。本期支持 A 股、交易所 ETF 和场外基金；实测 14 条持仓覆盖以下类别（**判定按下表从上到下短路匹配，基金分支最先判**）：

| 类别 | 判定（自上而下短路） | positions 里的值 | daily_bars secid | 抓取方式 |
|---|---|---|---|---|
| 场外基金（**最先判**） | `quote_secid` 以 `150.` 开头，**或** `market` 含「基金」，**或** code 在交易所接口取不到数但 pingzhongdata 有净值 | `150.014662` / 空+基金 / `001557`(实为基金,market 标错) | **独立前缀 `OF.014662`** | `fetchFundNavHistory` |
| 已有交易所 secid 的 A 股 / ETF | 未命中基金分支，且 `quote_secid` 匹配 `^(0\|1)\.\d{6}$` | `1.588170` | 原样 `1.588170` | `fetchHistoricalExchangeBars` |
| 空 secid 的 A 股 / ETF | 未命中基金分支，`quote_secid` 为空，`market` 属交易所支持列表，且 `code` 为 6 位数字，且交易所接口能取到数 | `159995`、`159915` | 按市场与代码补 `0.` / `1.` | `fetchHistoricalExchangeBars` |
| 不支持的资产 | 港股、美股、无法确认币种或无法归一化 | `105.xxx` / 缺 code | 无 | `skipped`，记录原因 |

> ⚠️ **`market` 字段不可信（实测 2026-07-13）**：持仓 `001557` 库内 `market="深市主板"`，但 suggest 实测其为 `150.001557 天弘中证500指数增强C`（场外基金，2686 个净值点），`0.001557`/`1.001557` 交易所接口均取不到数。故约束 0 除了看 `market`/`150.` 前缀，还需**用"pingzhongdata 能否取到净值"作最终兜底**——凡 pingzhongdata 有净值序列的，一律归 `OF.`，不进交易所分支。

> ⚠️ **顺序不可交换**：必须先判基金再判交易所。若先按 code 号段推断，`163806`（LOF 同码）、`16x/18x` 号段的场外基金会被误判成场内证券（见下方约束 0 实测）。

**关键约束**：

0. **判定优先级写死：基金分支最先判、且短路**。`resolveBarSecid` 必须先判「场外基金」——`quote_secid` 以 `150.` 开头 **或** `market` 含「基金」二字——命中就直接归到 `OF.{code}`，**绝不进入 §2/§3 的 code 号段推断**。原因（实测 2026-07-13）：持仓 `163806` 经东财 suggest 返回**两条同码不同证券**——`0.163806 中银稳健增利`（场内 LOF）与 `150.163806 中银增利债券A`（场外，用户实际持有）。若 `163806`（空 secid、market=基金）落入「`16` 开头→深市 `0.`」规则，会生成真实存在的 `0.163806`，抓到场内 LOF 的交易价而非用户持有的场外净值，且**能取到数、不报错**，属静默错配。LOF、分级基金等场内外同 6 位码的品种都靠这条优先级兜底。
   - **`market` 字段不可信，需 pingzhongdata 兜底（实测）**：持仓 `001557` 库内 `market="深市主板"`，实际是 `150.001557 天弘中证500指数增强C`（场外基金，2686 净值点），`0./1.001557` 交易所接口均无数据。故当 `market` 既非「基金」、code 又在交易所接口取不到数时，采集层必须**回退试 pingzhongdata**：能取到净值就归 `OF.`，否则才 `skipped`。即"能在 pingzhongdata 取到净值"是场外基金的最终判据，凌驾于 `market` 字段之上。
1. `150.` 是本项目合成前缀，**东财 K 线接口对 `150.xxxxxx` 不返回数据**（实测），必须抠出 6 位 code 走基金净值接口。
2. 基金在 `daily_bars` **必须用独立前缀（建议 `OF.`）**，不能用裸 6 位 code——否则 `159995`（ETF code）与某基金 code 理论上可能撞主键。ETF 用东财原生 `1./0.` 前缀，基金用 `OF.`，两个命名空间隔离。
3. 支持市场集合固定为 `A股`、`ETF`、`深市主板`、`沪市主板`、`科创板`、`创业板`；**「基金」不在交易所分支的支持列表内**（已被约束 0 提前短路到 `OF.` 分支），避免与 code 号段推断产生二义命中。
4. 深市 / 沪市前缀判定：`market` 先决定资产属于 A 股市场，再按代码映射；`0/15/16/18` 开头→深市 `0.`，`5/6` 开头→沪市 `1.`。本项目 `market-data.js` 无现成「market + code→东财 secid」纯函数，需新增 `exchangeSecidFromCode(code, market)`，避免把基金代码误判成交易所证券。**注意 `16`/`18` 开头号段与 LOF/场外基金高度重叠，此分支只能在约束 0 短路之后、对确属交易所证券的持仓生效。**

归一化产出统一契约：
```js
resolveBarSecid(position) → {
  secid,          // daily_bars 主键，如 "1.588170" / "0.159995" / "OF.014662"
  kind,           // "exchange" | "fund"
  fetchCode,      // 基金用 6 位 code；交易所证券用东财 secid
  currency: "CNY"
} | null          // 不支持或无法归一化时返回 null，记 coverage.skipped
```
> ⚠️ **采集层与查询层必须产出同一个 secid，否则查询按 A 读、数据落在 B 下 → 永远 `no-bars`**。`resolveBarSecid` 是纯函数，仅凭 `quote_secid`/`market`/code 号段判定，**不做网络探测**（查询层要快、且不能每次现探）。但 `market` 字段实测不可信（`001557` 标成"深市主板"实为场外基金），纯规则无法 100% 判对。**处置：新增 `secid_map` 表持久化"code→已确定 secid"（见 §6.3）**——首次回补时采集层对纯规则判为 exchange 但交易所 `no-bars` 的标的回退试基金接口，成功则以 `OF.` 落 `daily_bars` 并写 `secid_map`。此后 `resolveBarSecid` 先查 `secid_map`、命中即用，两层恒一致。查询层**只读库、不自行探测**（保持"查询只读库"与低时延）。

## 四、后端实现细节

### 4.1 新增：基金历史净值抓取 `fetchFundNavHistory(code)`

放在 `server/services/market-data.js`（与 `parseEastmoneyFundPage` 同源）。保留 `readJsArrayVar` 为模块私有函数，新增纯函数 `parseFundNavHistory(text)` 供单测；不为复用而扩大通用解析器的导出面。

```js
// 抓取场外基金完整历史「前复权净值」序列 [{date, close}]。
// close = 前复权净值 = 最新单位净值 × 累计净值(t) / 最新累计净值（§1.3 口径③）。
// 既消除分红假暴跌（涨跌率取自累计净值），又保证末点=最新单位净值（与成本/概览口径一致，不虚高）。
export async function fetchFundNavHistory(code, { fetchImpl = globalThis.fetch } = {}) {
  if (!/^\d{6}$/.test(code)) return [];
  const url = `https://fund.eastmoney.com/pingzhongdata/${code}.js?v=${Date.now()}`;
  const text = await fetchTextWithRetry(url, { fetchImpl, timeout: 8000 });
  return parseFundNavHistory(text);
}
```
`parseFundNavHistory(text)` 的约束：
- 读取 **`Data_ACWorthTrend`（累计净值，元素为 `[x(ms), y]` 二维数组）** 作为涨跌形态来源；读取 `Data_netWorthTrend`（`{x,y,equityReturn}` 对象数组）末点作为**最新单位净值锚点**。
- 计算 `factor = 最新单位净值 / 最新累计净值`，输出 `close = factor × 累计净值(t)`。这样 `close(最新)=最新单位净值`（末点与 `getOverview` 口径一致，不虚高 55%），而历史涨跌率完全等于累计净值涨跌率（消除分红假跌）。
- 用 `localDate(new Date(Number(x)), "Asia/Shanghai")` 转换日期；过滤非正净值；升序排序；同一天保留最后一个有效点。
- **两序列按日期对齐**（累计净值点数应与单位净值一致，实测 `163806` 两者均 4286 点）；某日缺累计净值则跳过该日。
- 若 `Data_ACWorthTrend` 整体缺失（个别老基金）则降级直接用 `Data_netWorthTrend.y`（等价于 factor=1，退化为单位净值），并在返回里标注 `navKind:"unit"` 供上层提示可能存在分红缺口。
- HTTP 非 2xx、超时、网络错误向调用方抛出；合法响应但无有效点返回 `[]`。

### 4.1.1 新增：交易所历史日线回补

在 `server/services/kline-store.js` 新增 `fetchHistoricalExchangeBars(secid, { fetchImpl, adjustment: "qfq", chunkSize: 2000, maxChunks: 100 })`，返回 `{ bars, truncated, requests }`：

1. 首次请求 `beg=0&end=20500101&lmt=chunkSize&fqt=1`（**前复权**）。
2. 当结果达到分页大小时，把当前最早日期减一天作为下一次 `end`，继续向前请求。
3. 以 `date` 去重，检测"最早日期没有继续向前推进"后停止，避免接口异常造成死循环。
4. 返回日期升序、收盘价为正且有限的 `{date,close,volume}`；达到 `maxChunks` 时返回 `truncated:true`，接口和 UI 必须披露历史可能被截断。

组合历史与压力监控**统一使用 `fqt=1` 前复权**。原因见 §1.3：`fqt=0` 不复权在 ETF 份额折算日（实测 159995/588170）会出现 -50%~-67% 假暴跌；且 `daily_bars` 主键 `(secid,date)` 无法承载同一 secid 的两种复权口径。既有 `fetchDailyBars` 已用 `fqt=1`，本函数与之口径一致，同 secid 混写不再互相污染。

> **实测提示（2026-07-13）**：东财该接口 `lmt` 非硬上限——`159915` 以 `lmt=2000` 请求实返 **3540 条**（2011-12 至今全量）。即多数标的 `beg=0` 一次即可拉全，`chunkSize/maxChunks` 游标分页在当前数据规模下基本不会触发。分页逻辑仍需保留（以"最早日期不再向前推进即停"为**主**停止条件，`maxChunks` 仅作死循环兜底），但实现者应预期常态是"一次拉全、`requests=1`、`truncated=false`"，勿因分页从未触发而误判逻辑有误。

### 4.2 新增：组合曲线纯函数 `buildPortfolioSeries()`

放在新文件 `lib/portfolio-series.js`（纯函数、无 I/O，仿 `lib/pressure-index.js`），便于单测。

```js
// 输入：holdings=[{secid, shares, cost, hasCost}], barsBySecid={secid:[{date,close}]（升序）}
// 输出：[{date, marketValue, pnl, pnlPct, coveredCount}]，按日期升序。
// 口径见设计文档 §1.2：市值=Σ_{i∈S(t)} shares×close(该日)；缺某标的当日价用「最近的前值」填充（forward-fill），
// 使各标的交易日历不一致（ETF 走 A 股日历、QDII 基金有滞后）时组合曲线不断点。
export function buildPortfolioSeries(holdings, barsBySecid) {
  // 1) 全体标的 date 并集（升序）
  // 2) 每标的建 date→close 映射 + 一个 forward-fill 游标 + started 标记
  // 3) 逐日：S(t) = 已出现过首个净值点的标的集合（避免上市前虚增）
  //    marketValue = Σ_{i∈S(t)} shares_i × ffClose_i
  //    【关键】totalCost 必须随 S(t) 动态：totalCost(t) = Σ_{i∈S(t) 且 hasCost} shares_i × cost_i
  //            —— 分子(市值)与分母(成本)始终对同一集合 S(t)，否则 range=all 早期出现 -90% 假暴亏（§1.2.1 实测）
  //    pnl = Σ_{i∈S(t) 且 hasCost}(shares_i×ffClose_i) − totalCost(t)
  //    pnlPct = totalCost(t) ? pnl/totalCost(t)*100 : null
  //    coveredCount = |S(t)|（供接口计算 fullCoverageSince、前端标注成分未齐区间）
  // 返回逐日点；所有数值必须为有限数，空仓返回空序列，pnlPct 无成本时为 null。
}
```

**口径对齐要点**：盈亏只对 `hasCost` 的持仓计算市值差（复用 `src/lib/portfolio-analysis.js:44-61` `getOverview` 的 `costedMarketValue - cost` 口径）。**成本基线随 S(t) 动态收敛**——这是与 `getOverview`（静态全量）的关键差异，只有当 S(t) 集齐全部持仓（末段）时两者才收敛一致。当 `coverage.positionCoverage === 100` 且 `coverage.costCoverage === 100` 时，曲线最后一个点才验收为约等于当前概览；允许的差异包括最新收盘价、基金净值披露滞后和盘中实时价。

**forward-fill 的必要性**：QDII 基金（如天弘纳指、华夏全球科技）净值披露比 A 股晚一天，各标的交易日历不完全一致。用 date 并集 + 前值填充，避免 inner-join 把不齐的日子全丢掉导致曲线稀疏。标的在其首个净值点之前不计入市值（`started` 标记）；`coveredCount` 逐日暴露成分入场进度；最新点继续保留 `lastDate` 与 `staleDays`，前端必须披露滞后。

### 4.3 新增：采集编排 `syncPortfolioBars()`

```js
import db from "./db.js";

export async function syncPortfolioBars({ fetchImpl = globalThis.fetch } = {}) {
  const positions = getPositions();
  const results = [];
  const fetched = new Set();
  for (const p of positions) {
    const resolved = resolveBarSecid(p);          // §三
    if (!resolved) { results.push({ code: p.code, ok: false, reason: "unsupported-or-no-secid" }); continue; }
    if (fetched.has(resolved.secid)) {
      results.push({ code: p.code, secid: resolved.secid, ok: true, reused: true });
      continue;
    }
    try {
      const fetchedBars = resolved.kind === "fund"
        ? { bars: await fetchFundNavHistory(resolved.fetchCode, { fetchImpl }), truncated: false, requests: 1 }
        : await fetchHistoricalExchangeBars(resolved.secid, { fetchImpl, adjustment: "qfq" });
      const { bars, truncated, requests } = fetchedBars;
      if (!bars.length) throw new Error("no-bars");
      upsertBars(resolved.secid, bars);
      fetched.add(resolved.secid);
      results.push({ code: p.code, secid: resolved.secid, ok: true, count: bars.length, truncated, requests });
    } catch (err) {
      results.push({ code: p.code, ok: false, reason: err.message });
    }
  }
  db.prepare("INSERT OR REPLACE INTO settings (key,value) VALUES (?,?)")
    .run("lastPortfolioHistorySync", JSON.stringify(summarizePortfolioSync(results)));
  return results;
}
```
> `upsertBars` 导出为 kline store 的持久化边界；采集层对空结果统一记为失败。相同 secid 一次回补，多条持仓复用结果。`lastPortfolioHistorySync` 保存 `ranAt`、成功/失败/skipped 数和 `truncatedSecids`，查询接口透传这份状态。
> ⚠️ **`upsertBars` 现有签名是 3 参 `upsertBars(secid, bars, now)`（`kline-store.js:98`）且未导出**。导出时需二选一：① 补默认值 `now = new Date().toISOString()`，让上面 2 参调用合法（推荐，向后兼容 `syncDailyBars` 的现有 3 参调用）；② 上面调用改为显式传 `now`。否则 `updated_at` 会写成 `null`。落地时以此为准修正 §4.3 代码。

### 4.4 新增：查询路由 `GET /api/portfolio/history`

`server/routes/portfolio-history.js`：
```js
import { getPositions } from "./stocks.js";
import { getAllBars } from "../services/kline-store.js";
import { resolveBarSecid, getPortfolioHistorySyncStatus } from "../services/portfolio-history.js";
import { buildPortfolioSeries } from "../../lib/portfolio-series.js";
import { localDate } from "../../lib/datetime.js";

const RANGE_DAYS = { "6m": 190 }; // 半年约 126 交易日，留冗余按自然日 190 截取
const DAY_MS = 24 * 60 * 60 * 1000;

export function getPortfolioHistory({ range = "6m", now = new Date() } = {}) {
  if (range !== "6m" && range !== "all") {
    throw Object.assign(new Error("range must be 6m or all"), { statusCode: 400 });
  }
  const positions = getPositions();
  const holdings = [];
  const barsBySecid = {};
  const skipped = [];
  const assets = [];
  for (const p of positions) {
    const resolved = resolveBarSecid(p);
    if (!resolved) {
      skipped.push({ code: p.code, name: p.name, reason: "unsupported-or-no-secid" });
      continue;
    }
    const bars = getAllBars(resolved.secid);
    if (!bars.length) {
      skipped.push({ code: p.code, name: p.name, secid: resolved.secid, reason: "no-bars" });
      continue;
    }
    holdings.push({ secid: resolved.secid, shares: Number(p.shares || 0), cost: Number(p.cost || 0), hasCost: Number(p.cost || 0) > 0 });
    barsBySecid[resolved.secid] = bars;
    assets.push({ code: p.code, name: p.name, secid: resolved.secid, firstDate: bars[0].date, lastDate: bars.at(-1).date, barCount: bars.length });
  }
  let series = buildPortfolioSeries(holdings, barsBySecid);
  const asOf = series.at(-1)?.date || null;
  // 成分全齐日：coveredCount 首次等于 holdings.length 的日期（range=all 早于此日的区间成分未齐，前端须标注）
  const fullCoverageSince = series.find((p) => p.coveredCount === holdings.length)?.date || null;
  if (range === "6m") {
    const cutoff = localDate(new Date(now.getTime() - RANGE_DAYS[range] * DAY_MS));
    series = series.filter((p) => p.date >= cutoff);
  }
  for (const asset of assets) {
    asset.staleDays = asOf ? calendarDaysBetween(asset.lastDate, asOf) : null;
  }
  const totalCost = positions.reduce((sum, p) => sum + (Number(p.cost) > 0 ? Number(p.shares || 0) * Number(p.cost) : 0), 0);
  const coveredCost = holdings.reduce((sum, p) => sum + (p.hasCost ? p.shares * p.cost : 0), 0);
  return {
    range,
    basis: "current-holdings",
    calculationScope: holdings.length === positions.length ? "current-holdings" : "covered-holdings",
    asOf,
    fullCoverageSince,       // range=all 时前端据此标注"成分未集齐"区间
    syncStatus: getPortfolioHistorySyncStatus(),
    series,
    coverage: {
      total: positions.length,
      covered: holdings.length,
      positionCoverage: positions.length ? holdings.length / positions.length * 100 : 100,
      costCoverage: totalCost ? coveredCost / totalCost * 100 : 100,
      skipped,
      assets
    },
  };
}

function calendarDaysBetween(start, end) {
  return Math.max(0, Math.round((Date.parse(`${end}T00:00:00Z`) - Date.parse(`${start}T00:00:00Z`)) / DAY_MS));
}
```

export const portfolioHistory = signal({ status: "idle", series: [], coverage: null, range: "6m", error: "" });
let portfolioHistoryRequestId = 0;

export async function loadPortfolioHistory(range = "6m") {

}

`market` 字段实测不可信（`001557` 标"深市主板"实为场外基金），`resolveBarSecid` 纯规则无法 100% 判对场内外同码 / market 错标的基金。**新增一张小表持久化"code → 已确定 secid"映射**，让采集层的 pingzhongdata 探测结果对查询层可见，两层恒一致：

```sql
CREATE TABLE IF NOT EXISTS secid_map (
  code TEXT PRIMARY KEY,   -- 6 位持仓 code
  secid TEXT NOT NULL,     -- 已确定的 daily_bars 主键，如 OF.001557 / 1.588170 / 0.159995
  kind TEXT NOT NULL,      -- "exchange" | "fund"
  resolved_at TEXT         -- 探测/确定时间
);
```

- **写入**：`syncPortfolioBars` 首次回补时，若 `resolveBarSecid` 纯规则判为 exchange 但交易所接口 `no-bars`，回退试 `fetchFundNavHistory`；成功则以 `OF.{code}` 落 `daily_bars` 并 UPSERT 一行 `secid_map`。规则能直接判定（`150.`/明确 ETF secid）的也顺带写入，作为缓存。
- **读取**：`resolveBarSecid` 先查 `secid_map`，命中直接用；未命中才走纯规则首选归类。查询层因此**只读库、零网络探测**，保持低时延。
- 属加表不改业务表，`positions` 不动，与"曲线是派生数据不落回业务表"原则一致。

### 6.4 无需改动

- `daily_bars` 表结构、索引：沿用现有（`db.js:30,41`），无 DDL 变更。
- `positions` 表：不加字段（曲线是派生数据；归类映射落在独立的 `secid_map` 表）。

## 八、成本与风险

**工作量估计**：后端采集 + 归一化 + 纯函数约 1 天（含单测），前端曲线组件约 0.5~1 天，联调回归 0.5 天，合计 **约 2~2.5 人天**。

**主要风险**：

1. **口径误读**（最高优先级）：用户可能把「当前仓位回溯曲线」当成真实账户历史。缓解：UI 强制口径提示 + 副标题说明。
2. **基金日期与净值滞后**：东财时间戳按北京时间解释；QDII 基金可能晚 1~2 天，个别基金可能长期无更新。缓解：Asia/Shanghai 转换 + forward-fill + `asOf/staleDays` 提示。
3. **数据源不稳定**：东财 pingzhongdata / push2his 偶发超时。缓解：统一超时与重试；非 2xx、空响应和网络错误分别记录；采集失败不阻断日更，下次重跑幂等补齐。
4. **历史接口分页异常**：分页游标可能重复或接口返回固定窗口。缓解：按日期去重、检测最早日期推进、设置最大分页次数并记录截断状态。
5. **首次上线数据回补**：独立使用 `POST /api/portfolio/history/sync`，避免用完整日更承担首次回补副作用；日更继续作为定期增量回补入口。
6. **人为价格跳变（复权 / 分红 / 折算）导致假暴跌**（实测已发生）：ETF 份额折算（`159995`/`588170`）与基金分红（`163806`）会在原始价 / 单位净值序列上制造 -50%~-11% 的伪断崖。缓解：ETF 取 `fqt=1` 前复权、基金取 `Data_ACWorthTrend` 累计净值（§1.3）；验收 P1-1、P1-6 强制回归折算日 / 分红日无断崖。
7. **场外基金与场内证券号段重叠（LOF / 分级）**（实测已发生）：`163806` 等场外基金 6 位码与场内 LOF 同码，机械号段推断会静默错配。缓解：§三约束 0 把基金分支写死为最先短路，验收 P1-2 用 `163806` 断言归 `OF.` 而非 `0.163806`。
