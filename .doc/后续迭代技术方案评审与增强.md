## 2. 【最高优先级修正】Storage Migration：sql.js → better-sqlite3 不是"API 几乎兼容"

原方案 §3.1 / §7.3 写"上层不感知 Adapter 变化""API 几乎兼容"。核对代码后，**这个判断偏乐观，有 3 个会直接抛异常或行为变化的点**，Adapter 必须显式兜住，否则迁移当天就崩。

### 2.1 `undefined` 绑定：当前是"隐式救命逻辑"，better-sqlite3 会直接抛错 —— 【P0 必改】

现状 `db.js:61`：
```js
run(...params) { db.run(sql, params.map(v => v === undefined ? null : v)); ... }
```
这个 `undefined → null` 映射是**载荷逻辑（load-bearing），不是可有可无的防御**。证据：`insertReport`（`reports.js:68-73`）把 `report.wikiPath / report.accent / report.originLabel` 直接塞进 `run()`，这些字段在部分导入路径下可能是 `undefined`。

better-sqlite3 的行为：绑定 `undefined` 抛 `TypeError: SQLite3 can only bind numbers, strings, bigints, buffers, and null`。

**修正要求**：新 Adapter 的 `run/get/all` 必须**保留同一套参数归一化**（`undefined→null`，布尔→`0/1`），作为 Adapter 内部契约显式实现，并写注释说明"这是从 sql.js wrapper 继承的载荷行为，勿删"。这条要写进 §3.1 的 Implementation，不能只说"保留 DDL 和 ALTER"。

### 2.2 布尔绑定：现状侥幸没踩，但 Adapter 要主动归一化

`toggleAutomation`（`settings.js:35`）存的是 `JSON.stringify(boolean)` → 字符串，侥幸安全。但 better-sqlite3 同样**拒绝裸布尔**。归一化层要统一把 `true/false → 1/0`，避免后续新增 SQL 直接绑布尔时才暴雷。

### 2.3 顶层 await 消失：简化，但要确认导入时序

现状 `db.js:12` 是 `const SQL = await initSqlJs()`（顶层 await，模块异步 settle）。better-sqlite3 是**同步构造器**，`await` 消失、模块变同步。这本身是好事（`server/index.js:7` 等同步 import 更简单），但要验证：无任何模块依赖"db 模块首次 import 后微任务队列已 flush"的隐式时序（当前未发现，但迁移后需一次 `npm test` + 真实起服务确认）。

### 2.4 `.changes` 返回契约：保持不变但要测

三处依赖 `.run().changes`（`stocks.js:24,62`、`signals.js:88`）。sql.js 用 `getRowsModified()`，better-sqlite3 原生返回 `{ changes, lastInsertRowid }`。**语义一致，但 Adapter 的 `run()` 返回值 shape 必须继续暴露 `.changes`**（原方案 §3.1 Interface 只列了 `run(...)` 未列返回契约，需补）。建议 Adapter `run()` 直接返回 better-sqlite3 原生 result（已含 `.changes`），比现状 wrapper 还少一层包装。

### 2.5 Docker 原生编译：原方案 §12 只说"可能涉及"，实际是**确定要改** —— 【P0 必改】

better-sqlite3 是原生 C++ 插件，`npm ci` 时需编译工具链。当前 `Dockerfile:1` 用 `node:20-alpine`，**Alpine 的 musl libc + 缺 `python3/make/g++` 会导致 `deps` 阶段直接构建失败**。

| 方案 | 改动 | 取舍 |
|------|------|------|
| A（推荐）| `deps` 阶段加 `RUN apk add --no-cache python3 make g++`；确认 runtime 阶段带上 `node_modules` 里的 `.node` 预编译产物 | 最稳，镜像稍大 |
| B | 换基础镜像为 `node:20-slim`（Debian/glibc，better-sqlite3 有 prebuild） | 免装工具链，与现有 Alpine 习惯不一致 |

无论哪种，`docker compose up -d --build` 必须在迁移 PR 内实测通过，不能只测本地 `npm run build`。这条要从 §12 Risk **提级为 §7.3 Rollout 的阻塞验收项**。

> ⚠️ 连带影响：runtime 阶段是 `COPY --from=deps /app/node_modules`（`Dockerfile:19`）。better-sqlite3 的编译产物与 Node ABI 绑定，deps/runtime 必须是**同一 Node 版本、同一 libc**，否则运行时报 `NODE_MODULE_VERSION mismatch`。现状同为 `node:20-alpine` 满足，切镜像时要保持一致。

## 3. 【需求↔设计矛盾】全局搜索"刷新可恢复" vs hash query 推迟到 v0.4

- **需求 FR-2 明写**（需求 §6）："搜索词应保留在 URL hash 或全局 state 中，**刷新页面后可恢复**。"
- **原方案 §3.3 / Open Decision 3** 却把 hash query 持久化推到 v0.4，v0.3 只用 global signal 跳转。

**global signal 在刷新后必然丢失**（Preact signal 是内存态），所以 **v0.3 交付物无法满足 FR-2 的"刷新可恢复"**。这是硬矛盾，不是优先级问题。

**修正建议（二选一，推荐 A）**：

- **A（推荐）**：把 hash query 提到 v0.3。改动其实很小——`Layout.jsx` 搜索时 `location.hash = "#knowledge?q=" + encodeURIComponent(v)`；`app.jsx` 已在解析 hash，加一个 `parseHashQuery(hash)` 纯函数（可单测，契合原方案 §8"put parsing in a pure helper"）。一步到位满足 FR-2，且省去 v0.4 的二次返工。
- **B**：若坚持 v0.3 只做 global signal，则**需求 FR-2 的验收标准要同步降级**为"当次会话内可见"，并在需求文档标注"刷新恢复顺延 v0.4"。不能让需求与设计各说各话。

> 无论选哪个，都要落实原方案 Risk §12 已提到的：**搜索跳转前保护当前页未保存输入**（例如持仓录入表单填了一半时误触搜索不应丢数据）。

## 4. 【必改】Report Delete Flow 的删除顺序（v0.3 无事务下会产生孤儿文件）

原方案 §7.2 说 "v0.3 如果还在 sql.js，可先执行 DB delete，再 best-effort 删文件"。**这个顺序在 v0.3（无真事务）下有一致性缺陷**：

- 先删 DB 行、再删文件——若删文件失败，DB 已无记录但**孤儿 HTML 永久残留在 `data/reports/`**；且因记录已删，`reportFileExists`（`reports.js:113`）再也扫不到它、无法清理。

**修正（v0.3，sql.js 下的正确删序）**：
1. Auth check。
2. 按 id 读 report，拿 `file` 路径。
3. **先删文件**（`fileDeleted = tryUnlink(path)`；`ENOENT` 视为成功→`fileDeleted:false`）。
4. 再删 DB 行。
5. 写 `report_delete` 日志（含 id/title/fileDeleted）。
6. 返回 `{ deleted:true, fileDeleted }`。

理由：文件是"可再生的次要副本"，DB 行是"主索引"。**先删次要、后删主索引**——即便中间崩溃，最坏是"文件已删但记录还在"，此时列表页靠 `reportFileExists` 过滤天然不显示，用户可重删，无孤儿泄漏。方向与现有兜底逻辑一致。

到 v0.4（better-sqlite3）后：DB 删 + 日志入一个 `transaction`，文件删放在事务提交后做 best-effort——原方案 §7.2 的这半句是对的，保留。

**路径安全（原方案 §11 已提，需落到删除实现）**：删除只接受 DB 里存的 `file` 字段解析出的路径，`resolve` 后校验 `startsWith(REPORT_DIR)`（复用 `server/index.js:382` `serveFile` 同款防穿越逻辑），**绝不接受 client 传入的原始路径**。

## 5. Page Data Loading：方向对，但"保留 refresh 一段时间"要设退出条件

原方案 §3.5 拆分 `loadShellData / loadTodayData / ...` 的方向完全正确，能消除评审报告指出的两个真实浪费：

- `refresh()` 大锅拉取 status+reports+business+market（`store.js:17-19`）；
- **signals 被加载两次**：`refresh` 里 `loadBusiness` 已拉 signals（`store.js:52`），`Signals.jsx` 挂载又触发 `app.jsx:32` 的 `refresh` → 再拉一次。拆分后应让 Signals 页只走 `loadSignalsData()`。

**唯一补强**：原方案 §3.5 说"保留 `refresh()` 作为兼容 wrapper 一段时间"——**"一段时间"要有明确退出条件，否则会永久留下两套加载路径（正是要消除的问题）**。建议写死：`refresh()` 在 v0.4 拆分完成后**仅允许 `handleLogin` 首屏调用**，其余调用点（尤其 `app.jsx:32` 的路由级 refresh）必须在同一里程碑内清零；v0.5 起删除 `refresh()` 本体。可用一次 `grep -rn "refresh(" src/` 作为里程碑收尾的验收命令。

## 6. Task Execution：收敛方向对，但漏了"三处重复判定"这个真实技术债

原方案 §3.4 的短期收敛（隐藏自由建表单、只留每日简报）合理。但**遗漏了一个应在同一次改动里处理的重复**：判断"是否每日任务"的谓词被**逐字复制了三份**：

- `server/index.js:371` `isDailyMarketBriefingTask`
- `server/routes/tasks.js:70` `isDailyTask`
- `src/pages/Tasks.jsx:172` `isDailyTask`

三处都是 `task.id === "daily-research" || /每日市场简报|日更/.test(...)`。收敛任务页时，后端两处应合并为单一导出（如 `server/services/task-kinds.js` 的 `isDailyBriefingTask`），前端复用后端已返回的 `formatTask` 里的 `executable` 字段（`tasks.js:58` 已经算好了！`Tasks.jsx` 却没用，又自己判了一遍）。

**这直接支撑原方案 §3.4 的 Future Seam**：等引入 `TaskExecutorRegistry` 时，"任务→是否可执行"只有一个判定源，registry 落地成本才低。**建议把这条补进 v0.3 的任务页收敛，而非留到 Future。**

## 7. 【被静默丢弃】评审报告提出、但需求/原方案均未承接的 3 项

评审报告（`项目评审报告.md`）里有 3 个具体问题，在需求和原方案里都消失了。要么明确纳入某个里程碑，要么在 Open Decisions 里写清"暂不做及原因"，不应无声丢弃：

1. **决策页市场数据陈旧**（评审 2.2 / 3.2.1）：`createDailyDecision` 用 `getMarketData()` 内存缓存（`decisions.js:16`），非交易时段/刚启动为空 → "市场环境：待接入"。**建议**：并入 v0.5 投研闭环，决策生成时若 live 缓存为空，回退到 `market_indices` 表的 seed 值或最近一次快照，而非直接落"待接入"。
2. **今日历史列表不过滤归档**（评审 2.3）：`Today.jsx:81` `reports.value.filter(r => r.localDate !== today).slice(0, 20)` 未排除 `archived`。归档后仍在今日页历史区出现，与知识库归档语义冲突。**建议**：v0.3 顺手加 `.filter(r => !r.archived)`，成本一行。
3. **Settings LLM 展示 env 名不匹配**（评审 3.1 未点名，此处补）：`Settings.jsx:24` 读 `import.meta.env.VITE_LLM_API_URL`，但后端 `llmClient.js` 认的是 `FINANCE_KNOWLEDGE_LLM_API_URL / LLM_API_URL`（无 `VITE_` 前缀，且是后端 env）。**前端永远显示"未配置"，与后端实际配置脱节**，是误导性状态。**建议**：改由 `/api/status` 或 `/api/settings` 返回后端 `isLlmConfigured()` 结果（`llmClient.js:29` 已有此函数），前端展示该布尔，不要读 `import.meta.env`。

## 8. 数据模型与 API：原方案基本可用，两处小修

原方案 §4 的四张表（无 schema change 的 hard delete、`type`、`quote_overrides`、`report_asset_links`）设计合理，`report_asset_links` 的 `relation` 枚举也考虑周到。两点补强：

1. **`quote_overrides` 的回退触发点要写明**（§4.3 只说"live 失败则回退"）：当前行情读取在 `market-data.js:70` `getStockQuote`（后端）和 `Portfolio.jsx:121` `usePositionPrices`（前端）两处。回退逻辑**应放在后端 `getStockQuote`**（单一数据源出口），前端不感知，否则前端每个消费点都要重复回退判断。这也顺带为 §5 批量报价接口留好位置。
2. **导出接口的注入与体积**（§5 v0.5 `GET /api/export/*.csv`）：CSV 要做字段转义（标的名可能含逗号/引号/换行），建议用成熟的最小 CSV 序列化而非手拼字符串；`reports.json` 导出要**排除正文 HTML 和任何 settings 里的 env/token**（呼应 §11），只导元数据。

## 10. 验收 Gate（对原方案 §8 的强化）

原方案要求每个里程碑 `npm test && npm run build`。**补两条针对本次风险的 Gate**：

- **v0.4 存储迁移专项**：除单测外，必须 (a) 用**现网 `data/app.db` 副本**跑一次真实启动 + 关键读写路径（建报告/删报告/日更/切换页）；(b) `docker compose up -d --build` 起容器实测，确认 better-sqlite3 原生编译 + 运行通过。**"本地 build 通过"不作为存储迁移的完成标准**（呼应全局验证纪律："构建通过 ≠ 完成，必须运行时后验"）。
- **v0.3 删除专项**：三条删除测试（正常/文件缺失/id 不存在）+ 一次真实删除后确认 `data/reports/` 下无孤儿文件残留。

## 11. 结语

原方案是一份**成熟、可执行的技术设计**，模块化语言（Interface/Implementation/Adapter/Seam）用得专业，四段式演进节奏也稳。本文没有推翻它的任何决策，只是把 **5 个被乐观措辞掩盖的落地风险**（尤其 better-sqlite3 迁移的 `undefined` 绑定与 Docker 编译）、**1 个需求与设计的时序矛盾**（搜索刷新恢复）、**3 项被丢弃的评审项**显式化，并给出可直接执行的修正。

建议执行时以原方案为主干，本文作为对照 checklist：每个里程碑开工前对一遍本文对应章节的 ⚠️/➕ 项，收尾时跑一遍 §10 的 Gate。

> 说明：本文结论基于静态代码核对 + `npm test`（47 例全绿）+ `npm run build`（通过）。better-sqlite3 的编译失败、`undefined` 抛错、Docker 行为均为**基于其公开行为契约与当前代码调用点的推断**，未在本环境实际安装 better-sqlite3 验证；落地时以 §10 的运行时 Gate 为准。
