## 1. 结论

当前重构已完成大部分页面和 API 的 Python/React 移植，持仓、自选、报告个人态的 owner 归属正确，后端 159 个隔离测试全部通过。当前版本仍有 5 类发布阻断问题：

1. 12 篇旧服务报告被迁成私有，违反“旧服务所有报告均为共享”的明确规则。
2. SQLite 在切换后继续产生数据，PostgreSQL 缺 2 篇报告、36 条日线、12 条信号；根目录旧 Node 启动路径仍然可运行。
3. 后端测试直接连接业务数据库和业务报告目录，当前已残留 10 个已激活测试账号、18 个“测试标的”和 48 个测试报告 HTML。
4. “辩论决策”的技术、基本面、情绪证据没有完成真实接线；技术分析师只收到证券代码，多空环节只做观点分组，没有反驳调用。
5. 辩论任务的 Worker 当前未运行，2 条任务长期停在 `queued`；运行中取消、异常终态、Checkpoint 和恢复能力也未实现。

迁移校验脚本当前返回退出码 1，共 4 项失败。该版本尚未达到全量切换和发布验收标准。

前端二次复核进一步确认了一组 P1 级响应式缺陷。决策页在桌面端已经发生局部重叠；今日、决策、知识库、组合分析、信号、任务日志在移动端或 769px 临界宽度存在溢出、裁切、异常压缩或错误断点。此前“页面无横向溢出”的结论只检查了根文档宽度，遗漏了 `.app-main` 内部滚动和子元素超出父容器，现已在本报告第 7.2～7.4 节更正。

## 3. P0 发布阻断项

### P0-1 旧报告可见性迁移错误

**现状**

- PostgreSQL 共有 32 篇报告：20 篇 `shared`，12 篇 `private`。
- 12 篇私有报告全部来自旧服务的手动报告。
- 所有报告的 `owner_id` 都正确指向当前 `admin` 超管账号。
- 用户规则要求旧服务报告全部设置为共享。

**根因**

`backend/scripts/import_sqlite.py:201` 按 `origin` 推导可见性：自动化报告设为共享，手动报告设为私有。旧数据的共享规则应由迁移口径直接决定。

**影响**

- 普通成员无法看到 12 篇本应共享的历史研究报告。
- 知识库、导出、搜索、关联报告和辩论证据检索均会出现用户间不一致。

**修复验收**

- 迁移生成的 32 篇存量报告全部为 `shared`。
- 所有存量报告仍由 `admin` 持有，个人的已读/标星/归档继续保留在 `user_report_states`。
- 新导入报告继续按未来产品规则选择私有或发布共享，存量修复不影响新报告策略。

### P0-2 数据切换未封口，SQLite 与 PostgreSQL 已分叉

**实测差异**

| 数据 | SQLite 当前值 | PostgreSQL 当前值 | 差异 |
|---|---:|---:|---:|
| `reports` | 34 | 32 | PG 少 2 |
| `daily_bars` | 50,343 | 50,307 | PG 少 36 |
| `community_signals` | 115 | 103 | PG 少 12 |
| `positions` | 14 | 14 | 一致 |
| 旧 `stocks` → `watchlist_items` | 9 | 9 | 一致 |
| `decisions` | 10 | 10 | 一致 |
| `market_indices` | 7 | 7 | 一致 |

PostgreSQL 缺少的报告：

- `2026-07-15 每日市场简报`
- `2026-07-16 每日市场简报`

当前迁移脚本实测失败项：

```text
daily_bars 行数       PG=50307  SQLite=50343
community_signals     PG=103    SQLite=115
reports 行数          PG=32     SQLite=34
instruments 数量      PG=98，超出 stocks + positions 的迁移上界
```

**根因与证据**

- 技术方案要求迁移前停止 Node 服务和 SQLite 写入脚本：`.doc/投研工作台全栈重构技术方案-Review落实版.md:829-838`。
- 根目录 `package.json` 仍把 `npm run dev`、`npm start`、`npm run migrate` 指向旧 Node/SQLite 服务。
- 旧 `server/`、`src/`、`lib/` 共 107 个文件仍保留在工作树。
- 迁移后的 7 月 15 日、7 月 16 日报告只写入 SQLite，说明旧写路径仍在工作。该结论由数据日期和启动脚本共同支持。

**影响**

- 新服务的数据基线持续落后于旧库。
- 用户从不同启动方式进入时会看到两套数据。
- 继续开发会扩大补迁范围，并增加冲突合并成本。

**修复验收**

1. 先停止全部旧 Node/SQLite 写入进程和自动化任务。
2. 重新生成冷快照，记录 SHA-256、WAL 状态和迁移时间点。
3. 对缺失的 2 篇报告、36 条日线、12 条信号做增量补迁或从新冷快照全量重建。
4. 对每张旧表校验行数和主键集合。
5. 删除根目录旧启动路径和旧读写代码，保留只读归档所需的迁移材料。

### P0-3 测试直接污染业务数据库和报告目录

**当前残留**

- 10 个 `authz_*` 活跃成员账号。
- 测试代码中的统一密码为 `pass-1234`。
- 98 条 instruments 中有 18 条名称为“测试标的”。

3. 测试完成后删除数据库、报告文件和队列记录。
4. 在人工确认清单后清理当前 10 个测试账号、测试 instrument 和 48 个测试 HTML。
5. CI 增加“测试后业务库行数不变”的守卫。

**运行态证据**

- 当前只运行 `fk_postgres` 容器，API 和 Vite 在宿主机运行，Worker 未运行。
- 数据库已有 2 条辩论，状态全部为 `queued`。

**代码缺陷**

- 取消 API 只把业务行改为 `canceled`：`backend/app/api/decisions.py:148-160`。
- Worker 只在开始前检查一次取消状态：`backend/app/services/debate_runner.py:40-45`。
- 图运行期间和提交完成前没有再次检查取消；运行中的任务可能把 `canceled` 覆盖为 `done`。
- 执行器只捕获 `LlmUnavailable`：`backend/app/services/debate_runner.py:59-71`。宏观网络、LLM 网络、裁判解析和数据库异常可让业务行长期停在 `running`。
- 进度只写 10% 和 100%，没有阶段进度：`backend/app/services/debate_runner.py:46-50,73-82`。
- `g.compile()` 未传 `PostgresSaver`：`backend/app/agents/decision/graph.py:66-83`。

**修复验收**

2. 业务取消同时取消队列 job；每个图节点前后检查取消标记。
3. 捕获所有任务异常并写 `failed/error_code/error_message/finished_at`。
4. 各阶段写 `stage/progress`，页面展示阶段文案。
5. 接入 PostgreSQL Checkpoint、加密 serializer 和 resume API。
6. 集成测试覆盖：排队、领取、异常、重试、运行中取消、恢复、Worker 重启。

## 4. P1 高优先级问题

### P1-1 迁移脚本的“幂等”实现会清空新系统数据

`backend/scripts/import_sqlite.py:97-105` 会删除报告、持仓、自选、用户、instrument 等目标表，再重新灌入旧库。当前 PostgreSQL 已有新成员、Session、邀请码、LLM 配置、辩论和信号个人态，这些依赖表不在删除列表中。

再次运行可能产生两类结果：

- 外键约束使脚本中途失败；
- 新系统创建的账号和业务数据被删除。

迁移脚本应使用独立 staging schema、明确 migration id、主键级 upsert 和 dry-run ledger。当前脚本只适合一次性空库导入，不应标注为可安全重复执行。

### P1-2 缺失报告文件被标成 `ok`，各 API 口径互相冲突

**当前状态**

- PostgreSQL 有 5 条报告引用的 HTML 不存在。
- 这 5 条的 `content_status` 全部为 `ok`。
- 迁移脚本统一写 `content_status="ok"`：`backend/scripts/import_sqlite.py:201-209`。
- reconciliation 只把缺失文件写入 ledger：`backend/scripts/import_sqlite.py:282-293`，没有更新报告状态。
- `/reports` 隐藏缺失文件：`backend/app/api/reports.py:55-67`，知识库实际显示 27 篇。
- `/status` 直接统计全部可见数据库行：`backend/app/api/status.py:36-63`，页面显示 32 篇。
- 导出 API 也包含缺失文件的报告：`backend/app/api/exports.py:49-60`。

用户会同时看到“知识库总量 32”和 27 张报告卡片，导出文件又含 32 条。修复后统一以 `content_status` 表达 `ok/missing`，各 API 明确采用同一口径。

### P1-3 历史 decisions 没有 owner 字段，数据归属只靠超管路由隐含控制

- 技术方案要求历史 decisions 为 `private + owner=超管`：`.doc/投研工作台全栈重构技术方案-Review落实版.md:840-853`。
- `Decision` 模型没有 `owner_id` 或 `visibility`：`backend/app/models/system.py:59-73`。
- 导入函数也无法写 owner：`backend/scripts/import_sqlite.py:272-279`。
- 当前 GET API 通过 `require_superadmin` 实现只读访问。

当前访问控制有效，数据模型层仍缺少明确归属，后续角色调整、导出或后台任务很容易绕过这条隐含规则。

### P1-4 “辩论决策”请求字段被静默丢弃

API 接收 `horizon` 和 `question`：`backend/app/api/decisions.py:50-53`，创建 Debate 时没有保存或传给图：同文件 `:111-125`。前端把 horizon 固定为 `swing`，没有问题输入框：`frontend/src/pages/DecisionsPage.tsx:27-32`。

接口当前会接受用户输入并静默忽略。应把决策周期和问题存入 Debate，并纳入证据窗口、角色 prompt 和报告快照；也可从契约中删除尚未支持的字段。

### P1-5 组合风险分类会把正常风控文本普遍判成高风险

`backend/app/services/portfolio_analysis.py:16-24` 只要风险文案含“止损、跌破、失效、威胁”等词就判为高风险。AI 分析按产品要求普遍包含止损和证伪条件，因此当前 14 个持仓全部被归为高风险，风险权重显示 100%。同一页面又给出健康度 80 和“结构稳健”。

风险标签应来源于结构化评级，或至少区分“存在止损线”和“高风险暴露”。健康度标签也要与高风险权重设置一致的阈值语义。

### P1-6 邀请码管理页面缺失，README 描述与页面不一致

- 后端有创建/查询邀请码 API：`backend/app/api/auth.py:112-125`。
- 注册页要求输入邀请码。
- README 写明“仅超管在设置生成邀请码”：`README.md:55-59`。
- 当前设置页只有 BYOK：`frontend/src/pages/SettingsPage.tsx:22-90`。

超管无法通过前端创建邀请码，成员注册闭环需要手工调用 API。

### P1-7 旧每日决策归档没有前端入口

后端保留 `GET /api/v1/decisions` 的超管只读归档：`backend/app/api/decisions.py:27-46`，旧数据共 10 条。当前 React 决策页只查询 debates，没有加载或展示历史 decisions：`frontend/src/pages/DecisionsPage.tsx:8-89`。

辩论升级设计要求旧每日指南作为次要入口或折叠历史区保留：`.doc/决策模块多角色辩论升级设计与验收清单.md:207-210`。

### P1-9 报告删除按钮错误地把“私有”等同于“本人所有”

### P1-11 生产启动脚本会吞掉所有 Procrastinate schema 错误

### P1-12 当前真实辩论 E2E 脚本已经失效

`backend/scripts/e2e_debate.py` 仍读取根目录 `FINANCE_KNOWLEDGE_LLM_*`，直接构造全局 LLM 配置，并用手工编造的技术/基本面/情绪证据跑图。当前架构采用数据库中的逐用户 BYOK。该脚本也不入队、不落 Debate、不经过 Worker，无法验收真实闭环。
